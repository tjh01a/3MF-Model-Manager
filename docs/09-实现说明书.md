## 1. 全局结构

```
PrintShelf/
├── launch.js                 Electron 启动器（找 electron.exe、拼参数、透传退出码）
├── electron/                 主进程
│   ├── main.js               窗口 / 协议 / 单实例 / capture 截图 / 生命周期
│   ├── preload.js            contextBridge 暴露 window.shelf（方法白名单 + 事件白名单）
│   ├── ipc/index.js          全部 IPC handler（channel = shelf:<方法名>）
│   └── services.js           业务聚合层：把 core/* 装起来，供 IPC 调用
├── src/core/                 纯 Node 业务逻辑（不依赖 Electron，可单测）
│   ├── paths.js store.js library.js scanner.js watcher.js thumbs.js duplicates.js utils.js constants.js
│   ├── model3mf.js colors.js classify.js mesh3mf.js meshopt.js
│   ├── slicer.js u1convert.js u1patch.js orcapresets.js presetguard.js
│   └── printers.js bambu-mqtt.js moonraker.js
├── src/renderer/             渲染层（原生 ESM，无框架、无打包）
│   ├── index.html            DOM 契约 + 图标 sprite + 浮层骨架
│   ├── js/{app,state,api,utils}.js
│   ├── js/views/*.js         页面级视图（grid/sidebar/toolbar/...）
│   ├── js/components/*.js    可复用组件（含 sidebar-state.js / boot.js / editmode.js / quickopen.js）
│   └── styles/*.css          按职责拆 6 个文件
├── tests/                    10 套测试，满配 437 条断言（缺本机样本/Blender/Orca 时自动跳过部分）
├── tools/                    走查探针（含 probe-colors.js）/ 语法哨兵 / 图标脚本 / 转换 worker
├── build/                    图标资源
└── data/                     运行时数据（库、设置、缩略图、缓存、备份）
```

**进程分工一句话**：渲染层只管「显示 + 意图」，所有磁盘/网络/子进程操作都在主进程；渲染层通过 `window.shelf.xxx()` 发请求，通过 `shelf.on(事件)` 收推送。渲染层**不允许** require 任何 Node 模块（`sandbox: true` + `nodeIntegration: false`）。

## 2. 启动链路

### 2.1 启动顺序

```
node launch.js [参数]
  └─ 找到 electron 可执行文件 → 以项目根为 app 目录启动 electron
       └─ electron/main.js
            1. 解析参数（--smoke / --capture / --ui-script / --width / --height / --dev / --no-seed）
            2. registerSchemesAsPrivileged：app、shelf 两个自定义协议
            3. app.whenReady → 建 Services 实例（此时 **init 还没跑**）
            4. createWindow()：默认 1480×940，加载 app://local/index.html
               → index.html 内联 CSS 立刻画出 #boot-splash（首帧就有东西，不等 JS）
            5. await services.init()  ← 后端初始化期间页面一直显示启动动画
            6. registerIpc() / bridgeEvents() / printers.start()
               capture 时再 ensureSeedData()
            7. signalRendererReady() → 向所有窗口推 app:ready
               （preload 在 document-start 就监听，did-finish-load 还会补发一次，绝不会丢）
            8. schedulePresetCheck()：延时 1.5s 做 U1 预设体检，失败不影响启动
            9. 渲染层 whenBackendReady() 放行 → init() → bootstrap() → 首屏渲染
               → finishBoot('ready') 淡出并移除 #boot-splash（详见 §2.4 / A.1）
           10. 若给了 --ui-script：在页面里执行脚本，把返回值打到 stdout
           11. 若给了 --capture：等页面稳定后 webContents.capturePage 存 PNG 并退出
```

> **顺序不能倒**：窗口必须先于 `services.init()` 创建，否则启动期间是纯白窗口；
> 但渲染层又必须在 IPC handler 全注册完之后才能调 `api.bootstrap()`，否则会拿到「方法不存在」。
> 这两件事靠 `app:ready` 闸门同时满足，见 §2.4。

### 2.2 启动参数（`electron/main.js` 顶部解析）

| 参数 | 作用 | 备注 |
| --- | --- | --- |
| `--smoke` | 自检模式：隔离数据目录 + 不弹错误框 + 打印 `{"ok":true,"ipcHandlers":N}` | 数据目录 = 临时目录 `printshelf-smoke-<pid>` |
| `--capture=<png>` | 截图后退出 | 走**真实**数据目录，仍绕过单实例锁 |
| `--ui-script=<js>` | 截图前在页面执行脚本（走查/验证） | 脚本体被包成 `(async () => { ... })()`，可 `await`、可 `return` |
| `--width=<n>` / `--height=<n>` | 覆盖窗口尺寸（480–3840 / 360–2160） | 走查 `<760px` 侧栏抽屉断点用；capture 时最小窗口约束同步放宽 |
| `--dev` | 打开 DevTools | |
| `--no-seed` | 不自动灌示例数据 | 做破坏性测试时必须加 |
| `PRINTSHELF_DATA_DIR` | 覆盖数据目录 | 测试隔离的唯一开关，见 `paths.js` |

### 2.3 窗口与安全配置（别随手改）

| 配置 | 值 | 为什么 |
| --- | --- | --- |
| `contextIsolation` | `true` | 渲染层拿不到 preload 作用域 |
| `nodeIntegration` | `false` | 页面里没有 `require` |
| `sandbox` | `true` | preload 只用 `contextBridge`/`ipcRenderer`，开沙箱不破坏功能 |
| `app://` 协议 | standard + secure + supportFetchAPI + stream | 用来加载 `src/renderer` |
| `shelf://` 协议 | standard + secure + supportFetchAPI（**没有** bypassCSP/corsEnabled） | 只服务 `data/thumbs/` 下的图片 |
| 静态资源路径校验 | `file !== root && !file.startsWith(root + path.sep)` | 防 `renderer-xxx` 同前缀兄弟目录穿越 |
| 内部导航判断 | `new URL(url).origin === APP_ORIGIN` | 防 `app://localevil` 被当内部 |
| 未捕获异常 | 弹中文提示后 `app.quit()` | 主进程状态已不可信，静默继续只会白屏 |
| `did-fail-load` | 弹「界面加载失败」 | 否则是纯白窗口，用户不知道发生了什么 |
| 单实例锁 | `--smoke` / `--capture` 放行 | 截图与走查依赖真实数据，隔离会让脚本失效 |

> 已知风险：`--capture` 会与正在运行的实例共用数据目录（见 08 报告「剩余风险 3」）。

### 2.4 后端就绪闸门（`app:ready`）

窗口先建、后端后初始化，就必须有一个「后端可以接请求了」的信号，否则渲染层会在 IPC 注册完成前调用 `bootstrap()`。

三处必须同步（和 §4.2 的 IPC 三处同步是同一类陷阱）：

| 位置 | 职责 |
| --- | --- |
| `electron/main.js` | `signalRendererReady()` 在 `services.init()` + `registerIpc()` + `bridgeEvents()` 之后调用；对所有存活窗口 `webContents.send('app:ready')`；`did-finish-load` 里对已就绪的窗口补发一次 |
| `electron/preload.js` | `EVENTS` 加 `app:ready`；在 **document-start** 就 `ipcRenderer.on`，用 `backendReady` + `readyWaiters` 缓存信号；暴露 `shelf.whenReady()` |
| `src/renderer/js/api.js` | `whenBackendReady()` = `Promise.race([shelf.whenReady(), 8 秒兜底])`；兜底防止信号丢失导致永久白屏 |

`app.js` 的两处闸门：`DOMContentLoaded` 后先 `await whenBackendReady()` 再 `init()`；`bootstrap()` 开头再 `await` 一次（双保险）。
启动动画由 `finishBoot()` 在首次刷新完成后收尾；`init()` / `bootstrap()` 抛错时走 `bootFailed()`。控制器细节见 A.1。

> 主进程里任何「页面加载完就想调用 service」的逻辑，都要走 `schedulePresetCheck()` 的模式：
> 先判 `services.initialized`，再排到 `signalRendererReady()` 之后，否则极端时序下会打到未初始化的对象。

### 3.2 `store.js`：读写与安全

| 机制 | 做法 | 为什么 |
| --- | --- | --- |
| 读取 | `_readJson` → 失败进 `_readJsonRetry`（3 次，间隔递增） | 杀软占用/网络盘抖动是瞬时的，直接判损坏会误伤 |
| 损坏判定 | 只有**解析失败**才算 `corrupt`；读不到算 `unreadable` 并抛中文错误、**拒绝写入** | 以前两者混为一谈，一次瞬时占用就重置空库 |
| 写入 | `_atomicWrite`：写 `.tmp` → fsync → `rename` 覆盖 | 断电不会留半截 JSON |
| 串行化 | `_enqueue` 保证同一时刻只有一个写在跑 | 避免两个 update 交叉覆盖 |
| 备份 | `_shouldAutoBackup` + `_doBackup` + `_rotateBackups(keep)` | 出事能回到上一个好状态 |
| 恢复 | `_recoverFromBackups`：从最新备份回滚 | 仅在确认损坏时调用 |
| 变更通知 | `EventEmitter` → `services` 转发为 `lib:changed` | 渲染层据此刷新 |

**入口方法**：`init()`、`updateLibrary(mutator, reason)`、`updateSettings(patch)`、`backup/restoreBackup/exportTo/importFrom`。
所有业务只通过 `updateLibrary` 改库（它内部负责原子写 + 备份 + 通知）。

### 3.3 模型记录（`src/core/scanner.js` 里构造）

```js
{
  id,               // sha1(pathKey(path)).slice(0,20) —— 路径变了 id 就变
  path, fileName, ext:'3mf',
  folderId, relativePath,
  size, mtime, hash,          // hash 可选（设置里 hashEnabled）
  title,                       // 默认 = 文件名去扩展名，可被用户改
  createdAt, updatedAt,
  status: 'ok'|'missing'|'error', missingSince, parseError,
  meta: { /* 见 model3mf.js：objectCount / plateCount / 体积 / 耗材估算等 */ },
  thumbnail, thumbSource,
  categoryId, autoClassified, tagIds[], favorite, rating, note, sourceUrl, author,  // autoClassified 见 A.11
  printStatus: 'unprinted'|'queued'|'printing'|'printed'|'failed',
  printCount, lastPrintedAt, lastOpenedAt, openCount,
  duplicateGroup, duplicateOf, similarGroup,   // 由 duplicates.js 统一重算

```

> 重新扫描时以 `...(prev||{})` 打底，只覆盖技术字段 —— **人工字段（标题/分类/标签/评分/备注）不会被扫描冲掉**，这是硬约束。

### 3.4 `library.js`：业务方法分组

| 组 | 方法 |
| --- | --- |
| 查询 | `query(q)`（筛选/排序/分面）、`get`、`getMany`、`stats`、`smartCounts`、`roulette` |
| 改记录 | `update`、`bulk`、`rename`（只改标题）、`renameFile`（真改磁盘名，失败回滚）、`remove`（只出索引）、`relink`、`findRelinkCandidates`（异步限时遍历） |
| 打印状态 | `markOpened`、`setPrintStatus` |
| 分类 | `categories`、`categoryCreate/Update/Delete` |
| 标签 | `tags`、`tagCreate/Update/Delete`、`tagAssign(ids, tagIds, mode)` |
| 视图 | `views`、`viewSave`、`viewDelete` |
| 导入导出 | `exportJson`、`importJson` |

**筛选逻辑集中在 `query()`**：智能视图（all/favorites/recentOpened/unprinted/uncategorized/untagged/recent/printed/rated）+ 关键词 + 分类 + 标签（any/all）+ 打印状态 + 评分 + 排序 + 分页。加新筛选项 = 改 `state.query` 默认值 + `query()` 里加条件 + 侧栏/工具栏加入口。注意 2026-11-16 侧栏精简后，只有 all/favorites/recentOpened/printed/duplicates/missing 有侧栏入口，其余 query 语义仍在（历史保存视图、程序内跳转仍可用），别把底层能力一起删掉。

## 4. IPC 与事件

### 4.1 命名规则

- 全部 `ipcMain.handle('shelf:<方法名>')`，方法名与 `preload.js` 的 `METHODS` 数组一一对应。
- 渲染层统一用 `api.<方法名>(...)`（`src/renderer/js/api.js` 动态生成 proxy）。

### 4.2 三处必须同步改（最容易漏）

1. `electron/ipc/index.js` → `handlers` 里加一个函数
2. `electron/preload.js` → `METHODS` 数组加同名项
3. `src/renderer/js/api.js` → `METHODS` 数组加同名项

漏第 2 步：渲染层调用直接 `undefined is not a function`；
漏第 3 步：`api.xxx` 不存在。

### 4.3 错误约定

- 后端 `throw new Error('中文原因')`，**不要**抛英文技术错误。
- Electron 会把 reject 包成 `Error invoking remote method 'shelf:x': Error: ...`，`api.js` 的 `friendlyMessage()` 负责剥前缀，再统一 toast。
- 只读/浏览器直开时 `api` 返回 rejected Promise（提示「请在桌面应用中打开」），不会白屏。

### 4.4 推送事件（main → renderer）

| 事件 | 触发 | 消费方 |
| --- | --- | --- |
| `scan:progress` | 扫描进度 | `app.js` → 顶部进度条 |
| `lib:changed` | 库变更 | `api.js` → `shelf:refresh` → `doRefresh` |
| `watcher:changed` | 文件监听变更 | 同上 |
| `printers:update` | 打印机状态轮询 / MQTT 推送 | `devices.js` 实时刷新 |
| `u1:progress` / `u1:log` / `u1:cancelled` | 转换进度 | `openwith.js` 进度弹窗 |
| `mesh:progress/log/done/error` | 网格优化 | `components/meshopt.js` |
| `app:toast` / `app:error` | 主进程主动提示 | `toast.js` |

事件白名单在 `preload.js` 的 `EVENTS` 数组里，**加推送必须同步加白名单**，否则渲染层永远收不到（设备页「每 3 秒刷新」曾经就是假的，就是这个原因）。

## 5. 扫描 / 监听 / 缩略图

### 5.1 `scanner.js` 流程

```
scanAll / scanFolder / scanPath
  └─ _run(folders, force)
       1. 单飞锁：已在跑就直接抛「正在扫描中」（防止手动扫描与 watcher 撞车）
       2. walk：遍历目录，跳过排除项、自身数据目录、>500MB 文件
       3. 比对：size+mtime 都没变且 status==='ok' → unchanged（不重新解析）
       4. 并发限流解析 toProcess：parse3mf → 记录 → thumbs.ensureFor → 入库
       5. 收尾：标记缺失文件 status='missing'、重算重复组、写库、发 scan:done
```

**排除规则**：`isUnder(p, root)` + `normExclude`（Windows 大小写/斜杠归一）；`_selfDirs()` 永远排除自己的 `data/`。

**取消**：`cancel()` 置 `_cancelRequested`，worker 在每个文件边界检查，不做硬中断。

### 5.2 `watcher.js`

- chokidar 监听所有库目录，只关心 `.3mf`（大小写不敏感）。
- **800ms 防抖**合并事件到 `_pending`，定时 `_flush()`。
- 若此刻 `scanner.getStatus().running`：把这批塞回 `_pending`，1.2 秒后重试，**不硬闯**（硬闯会撞单飞锁并丢掉这批变更）。
- `_flush` 按所在目录归组，对每个目录 `scanFolder`（增量）。

### 5.3 `thumbs.js`

| 机制 | 说明 |
| --- | --- |
| 新鲜度 | `_isThumbFresh`：缩略图 mtime ≥ 源文件 mtime - 1s 才算新鲜（**3MF 内容变了要重生成**） |
| 生成 | 优先用 3MF 内嵌的 `Metadata/*.png`；没有则 `buildPlaceholderSvg` 生成占位图（首字 + 色相由路径 hash 决定） |
| 原子性 | 写 `.tmp` → rename |
| 复用 | `ensureFor(record, { parseResult })` 可由 scanner 传入解析结果，避免二次解压 |
| 失败 | 返回 null，**保留上一轮已生成的缩略图**（别因为一次抖动把封面清空） |
| 维护 | `regenerate(ids)`、`prune()`（清孤儿）、`stats()` |

## 6. 3MF 解析与网格优化

### 6.1 `model3mf.js`

职责：解压 3MF（本质是 zip），读出：
- `3dmodel.model` 的元信息（对象数、网格体积、包围盒）
- `Metadata/*.png`（内嵌缩略图，取第一张/封面）
- 多盘（plate）信息
- 耗材颜色 `meta.filamentColors` / `filamentTypes` / `colorSource`（详见 A.9）
- 对象名 `meta.objNames`（最多 12 个、每个 ≤60 字，自动分类用，详见 A.11.3）
- 返回 `{ ok, meta, thumbnail:{entry,data}, error }`

**不落临时文件**，全部在内存里；大文件（>500MB）在 scanner 阶段就被跳过。
只取颜色时用 `parse3mf(path, { withThumbnail:false })`：不解压 PNG，真实样本 2~13ms，
但 `hasThumbnail` 会降级为 false，所以**回填只能合并颜色字段，不能整体替换 meta**。

`src/core/colors.js` 的 `backfillFilamentColors(store)` 给旧库记录补颜色：
挑「没有 `meta.filamentColors` 且文件还在」的记录，每 12 条让出一次事件循环、总预算 8 秒
（超预算 `truncated:true`，只写回已解析部分，剩余记录下次启动继续），
结果攒齐后**一次性** `updateLibrary()`（只触发一次 `lib:changed` / 一次界面刷新）。

### 6.2 `mesh3mf.js` / `meshopt.js`

- `mesh3mf` 负责 zip 层：读条目 → 找网格块 → 写回（其余条目原样 copy）。
  - `replaceMeshGeometry(mesh.full, V, F)`：必须传**含 `<mesh>…</mesh>` 外壳**的字符串，否则写回后标签丢失。
  - 重建拓扑（深度档）时统计 `paintDropped`：三角面的 `paint_color` 无法保留，上层据此给明确警告。
- `meshopt` 负责档位：温和/标准/较强/深度（深度=重建拓扑，顶点数会变）。
  - `clampStats` 记录位移裁剪情况；`warnings` 合并内嵌解析警告 + 涂色丢失警告。
  - 可选外部 Blender（`blenderPath`，在设置页指定）做平滑/重网格。

## 7. 快造 U1 转换链路

### 7.1 `u1convert.js`

```
convert(id, opts)
  ├─ cacheKey(srcPath, {filamentPreset, processPreset})   // 内容指纹 + 预设指纹
  ├─ cachePathFor → data/u1-cache/<文件名>_U1_<hash>.3mf
  ├─ _inflight 表：同一 key 复用同一 Promise（双击不会起两个 worker 写同一产物）
  └─ _runConvert → new Worker(src/core/u1-worker.js)
        worker 内：读源 3MF → 生成快造可切片的配置 → 写 .part → patch 预设 → rename
        进度通过 worker.postMessage → u1:progress 事件
```

- **源文件永远只读**，产物只进 `data/u1-cache/`。
- `cancel()` 终止当前 worker；`clearCache({days})` 按保留天数清理。
- 缓存命中直接返回，不重跑（`cached: true`）。

### 7.2 `u1patch.js`

把用户选的耗材/工艺预设写进转换产物的 `Metadata/project_settings.config` / `model_settings.config`，并处理 BOM（之前「预设重启后消失」就是 BOM 导致的）。

### 7.3 `orcapresets.js`

- 扫描快造 Orca 的预设目录（系统目录 + 用户目录），建内存索引。
- `_stampOf(dirs)` 决定索引何时失效：
  - 系统目录：只看目录 mtime（几百个文件，热路径不能逐个 stat）
  - 用户目录：把每个 `json/info` 的 mtime+size 都算进 stamp（原地改预设必须能立刻读到新内容）
- 对外：`list()`、`find()`、`invalidate()`。

### 7.4 `presetguard.js`

- `snapshot(reason)`：把用户目录里的快照存到 `data/preset-backups/`。
- `restore(id)`：还原前做**路径穿越校验**（拒绝 `../..`），只允许写回预设根目录内部。
- `health()`：比对当前状态与快照，检测「被原版 Orca 覆盖」。
- 自动检查在 `services.u1PresetAutoCheck()`，设置页「预设保护」区块消费。

### 7.5 「用 Orca 打开」的两条路（2026-11-16）

`openWith(ids, which)` 的 `which` 从 2 个扩到 3 个：

| which | 目标程序 | 是否转换 | 说明 |
| --- | --- | --- | --- |
| `bambu` | Bambu Studio | 否 | 原文件直接打开 |
| `orca-official-direct` | 官方 OrcaSlicer（`orca-slicer.exe`） | 否 | 原文件直接打开；Orca 会沿用文件里原作者的机器配置（如 Bambu H2C），不是 U1 |
| `snapmaker` | 快造 Orca（`snapmaker-orca.exe`） | 是 | 自带完整 U1 预设，开箱即用 |
| `orca-official` | 官方 OrcaSlicer（`orca-slicer.exe`） | 是 | 需目标 Orca 已装 U1 完整机器预设，否则返回 `presetWarning` |

**为什么不能直接把拓竹 3MF 丢给 Orca（实测）**：

1. 原始拓竹 3MF 用官方 Orca 2.5.1 CLI 切片，G-code 里是 `printer_model = Bambu Lab H2C`、
   `printable_area = 330×320`、双喷嘴、`0.20mm Standard @BBL H2C`。Orca 会继承原作者的机器与工艺，
   切出来不是 U1 的，拿到 U1 上不能打。
2. 我们转换后的 U1 工程（579 个键，`printable_area=270×271`，
   `print_compatible_printers=["Snapmaker U1 (0.4 nozzle)"]`）交给官方 Orca 切，
   `printable_area` 反而退回 `200×200` 兜底 —— 官方 Orca 的 `resources/profiles/Snapmaker`
   里只有 U1 的床贴图，没有 machine JSON。
3. 用户在 Orca 里看到的 `Snapmaker U1` 用户预设可能只有 8 个键，`inherits` 指向不存在的父预设，
   继承链是悬空的。
4. 把快造 Orca 的整套预设（119 machine / 112 process / 316 filament）复制进临时 datadir 再喂给
   官方 Orca，报 `Preset was not found in the loaded bundle`：用户预设要在 Orca 里注册，
   不是复制文件就能用。

因此两条路都**必须先转换**；`presetWarning` 就是把第 2 条边界明说，不假装官方 Orca 能直接切对。
要彻底解决，得等 Orca 上游收录 U1 预设，或用户在 Orca 里装共享配置。

**菜单图标**：`src/renderer/assets/slicers/` 下三枚静态资源 —— `bambu-studio.png` / `orcaslicer.png`
是从各自 exe 提取的 48px PNG，`snapmaker-orca.svg` 取自快造 Orca 安装目录的
`resources/images/splash_app_icon.svg`（`rect fill="#171717"` + 白色 ∫ 字形）。
不用运行时 `app.getFileIcon`：实测它对 `snapmaker-orca.exe` 只返回 Windows 通用 exe 图标
（白底蓝窗口），对另外两个则正常。静态资源在 22px 下更清晰，也不增加 IPC 面。
`u1PresetForOrca(exePath)` 负责体检：先查安装目录 `resources/profiles/Snapmaker/machine/`，
再查 `%APPDATA%/OrcaSlicer/user/*/machine/`，只认带 `printable_area` 的完整预设。

## 8. 打印机

### 8.1 数据

`settings.printers[]`：`{ id, kind:'snapmaker'|'bambu', name, ip, serial, accessCode, model }`。

### 8.2 `printers.js`

- `start(intervalMs=3000)`：定时 `tick()` 轮询所有在列打印机。
- 快造：`_pollMoonraker`（HTTP `/printer/objects/query`），`_normalizeSnapmaker` 归一成统一结构（状态、进度、剩余时间、喷嘴/热床温度、耗材）。
- 拓竹：`_ensureBambu` 建 MQTT 长连接（见 §8.4），状态来自推送，轮询只做兜底。
- 统一结构：`{ state, stateText, job:{name,percent,remainMin}, temps:{nozzle,bed}, materials[] }`。
- `action(id, cmd)`：pause/resume/stop。
- `discover()`：按本机网段并发探测（48 并发，420ms 超时），拓竹额外读 serial/accessCode。
- **连不上时说什么**：`_bambuErrorText()` 把 `ECONNREFUSED / ETIMEDOUT / EHOSTUNREACH / ECONNRESET`
  翻成带 IP 和处置建议的中文（「IP 可能变了」或「没开局域网模式」）。不要再把 `connect ECONNREFUSED x.x.x.x:8883` 直接丢给用户。
- **自动纠正 IP**：DHCP 换地址是最常见的原因。连接报网络类错误时（`_isNetError`）后台调
  `_healBambuIp()`：扫本网段 8883 → 读证书 CN（= 序列号）→ 与本机配置的 `serial` 完全一致才
  改 `settings.printers[i].ip` 并重连。节流 5 分钟一次、每次运行最多 6 轮（云端模式下扫不到东西，
  不能一直刷局域网）。判据必须是「序列号相同」，不能只按「8883 开着」就改。
- **双通道**：`_pickChannel()` 按 `printer.mode` 决定走局域网还是云端——
  `auto`（默认）局域网优先、失败 3 秒后切云端、走云端时每 5 分钟探一次 8883 恢复就切回；
  `lan` / `cloud` 强制单通道。通道记在 `ent.channel`，状态里带 `via` 字段，设备卡显示「云端通道」。
  `_ensureBambu` 里云端客户端的参数是 `host=cn.mqtt.bambulab.com, username='u_'+uid, password=token`。

### 8.3 `bambucloud.js`

非官方云端接口封装（`api.bambulab.com` + `*.mqtt.bambulab.com`）：

| 方法 | 说明 |
| --- | --- |
| `login({account,password})` | 密码换 token；需要邮箱验证码时返回 `{needCode:true,tfaKey}`（不报错），UI 走第二步 `loginWithCode`（`code`/`tfaCode` 字段都试一次） |
| `devices()` | `GET /v1/iot-service/api/user/bind` → 序列号/名称/**访问码**/在线（拿到访问码用户就不用手抄） |
| `status()` | `{loggedIn, account, uid, expiresAt, expired}`，JWT 本地解析 |
| `mqttHost()` | `cn.mqtt.bambulab.com`（US/EU 备选在 `MQTT_HOSTS`） |

**安全约定**：密码只在登录瞬间用于换 token，**绝不落盘**；`settings.bambuCloud` 里只有 token/uid/账号。
UI 入口：设备页工具栏「拓竹账号」→ `components/bambuaccount.js`（两步式登录弹窗），
登录成功自动 `bambuCloudSync()`：按序列号合并打印机（存在就更新访问码，不存在就新增 `mode:'auto'`）。
对应 IPC：`bambuCloudStatus / bambuCloudLogin / bambuCloudLoginCode / bambuCloudLogout / bambuCloudSync`。

### 8.4 `bambu-mqtt.js`

- TLS MQTT（8883），`accessCode` 作密码，用户名 `bblp`。
- 报文是「16 字节头 + JSON」，**必须先校验长度再截取**（短包会让 `readUInt32LE` 抛 RangeError，而异常发生在 socket 回调里，会直接打崩主进程）。
- 断线重连：3 秒起，失败逐次翻倍，最多 30 秒。
- 解析 `print.state` / `mc_percent` / `mc_remaining_time` / 温度 / AMS。

### 8.5 `moonraker.js`

极简 HTTP 客户端（GET/POST + 超时 + 错误归一），只服务快造 U1。

## 9. 渲染层架构

### 9.0 智能视图与筛选的关系（容易被当成计数 bug）

侧栏徽标（`smartCounts`）和顶部统计条（`stats`）都是**全库口径**，而列表内容会叠加当前筛选。
于是「左写 79、右列 0」这种矛盾一定是筛选没清干净，不是计数算错。

约定：
- 点「重复文件 / 失效文件」时**自动清掉**分类 / 标签 / 关键词 / 收藏 / 评分筛选（`views/sidebar.js` 的 `onClick`），
  因为这两个是全库体检视图，带着分类进去必然为空。
- 用户在这个视图里**再手动加**筛选导致为空时，空态必须解释原因（`views/duplicates.js` 的 `filterHint()`）：
  「全库其实有 79 个重复文件，但当前筛选（分类）把它们挡住了」。
- 以后再加「全库性质」的智能视图（例如「大文件」），同样要在进入时清筛选，别让用户自己猜。

### 9.1 数据流

```
用户操作 → view/component 调 api.xxx()
        → 主进程处理 → 推 lib:changed
        → api.js 转成 window 事件 shelf:refresh
        → app.js scheduleRefresh(reason) 单飞合并 → runRefresh()
              ├─ reason ∈ UI_ONLY_REASONS → doLightRefresh()：只同步 DOM，不查库、不重建卡片
              └─ 其余 → doRefresh()：api.query/stats/smartCounts → setState → renderGrid()（增量）
```

`doRefresh` 还会刷新侧栏、工具栏、批量条、统计条、空状态、状态栏；
`doLightRefresh()` 只跑 `applyViewClass / renderSidebar / syncToolbar / syncBulkbar / renderStats / updateEmptyState / updateStatusBar`。
**筛选变化后必须裁剪选择集**（`pruneSelection`），否则批量删除会连看不见的条目一起删。
刷新单飞、增量渲染、缓存的全部细节见 **A.3**，改刷新逻辑前务必先读。

### 9.2 `state.js`

单一状态对象 + 订阅通知。关键字段：
`items/total/facets`（当前结果）、`query`（筛选条件）、`selection`（Set）、`activeId`、`categories/tags/views`、`stats/smartCounts`、`view/cardSize/theme`、`contentMode`、`editMode`、`sidebarCollapsed`、`ready`、`settings`。

`sidebarCollapsed` 与 `settings.ui.sidebarCollapsed` 是**同一件事的两份镜像**，不要直接改其中任何一个 —— 统一走 `components/sidebar-state.js` 的 `applySidebar()` / `toggleSidebar()`（见 A.2）。同理 `applyTheme()` 会同步 `settings.ui.theme`。

| 拖卡片 → 侧栏分类 | 归类（并飞入动画） | 同左 | `grid.onDragStart` + `sidebar.onDrop` |
| 从资源管理器拖文件进窗口 | 添加目录 + 扫描 | — | `app.bindDragDrop` |

### 10.2 编辑模式（`components/editmode.js`）

- **进入**：`enterEditMode(anchorId)` → `state.editMode = true`、`body.edit-mode`、创建/显示 `#editbar`、选中 anchor、首次进入弹一次提示。
- **操作条**：`全选 / 迁移到分类 / 删除 / 完成`。迁移与删除直接复用 bulkbar 的导出函数，不重写批量逻辑。
- **样式**：`body.edit-mode` 下勾选框常显（22px 圆角方块，选中变实心 + 白勾）、卡片加淡紫覆盖层、隐藏 `#bulkbar` 与 `#stats-actions`（避免两个入口重复）。
- **退出**：`exitEditMode()`；触发点有「完成」按钮、Esc、点空白处。
- **Esc 优先级**（`app.handleEsc`）：灯箱 > 弹窗 > 菜单 > **拓竹账号弹窗** > 设备 > 设置 > **编辑模式** > 详情 > 清空选择。
  新增浮层必须挂进这条链（`isXxxOpen()/closeXxx()`），否则 Esc 会先关掉底层浮层、把你的弹窗留在原地。

### 10.3 拖拽：内部移动 vs 外部导入

**投放必须过浏览器那一关（这是最容易「看起来实现好了其实从没生效」的地方）。**

拖动开始时 `dt.effectAllowed = 'copyMove'`（只允许 copy/move），那么目标元素的 `dragover` 里
`e.dataTransfer.dropEffect` **只能设 copy 或 move**。设成 `'link'` 之类不在集合里的值，Chromium 会把
本次操作判为 `none`：**高亮照常显示（那是我们自己加的 class），但 `drop` 事件根本不会触发**，
用户看到的就是「拖过去、目标亮了、松手没反应」。

排查方法：`node tools/drag-e2e.js`（见 §12.2），它用真实拖拽会话 + `Input.dispatchDragEvent` 复现，
并且能 A/B 对比（把 dropEffect 临时改回 `link`，会看到 dragleave 而不是 drop）。


这是踩过的坑：卡片里有 `<img>`，Chromium 拖动时会把图片塞进 `dataTransfer` 的 `Files` 里，于是窗口级 `dragenter` 判定成「从外面拖文件进来」，弹出了「松开即可添加」的遮罩。

约定：
- `grid.onDragStart` 给 `body` 加 `.drag-holding-card`；`dragend`/兜底定时器移除。
- `app.bindDragDrop` 的 `hasFiles(e)` **先看这个标记**，有就直接返回 false。
- 库内拖动期间，可投放的分类/标签会高亮（`.drag-holding-card #nav-categories .nav-item` 等）。
- 只有真正来自资源管理器的 `Files` 才走「添加目录 + 扫描」。

### 10.4 悬停打开菜单（`components/quickopen.js`）

- 触发：`mouseover` 命中 `.card-quick [data-act="open"]`；`mouseout` 移到菜单外才开始 160ms 关闭倒计时（移进菜单会 `cancelHide`）。
- 为什么挂到 `body`：`.card-media` 有 `overflow: hidden`（裁图片圆角），菜单放卡片里一定被裁掉。
- 定位：`getBoundingClientRect` + 上下翻转 + 左右夹取，动画结束后（220ms）再校一次。
- 选项：`data-pick="bambu"`（原文件直接开）/ `"snapmaker"`（先转换再开）。
- 直接点按钮本身 = 按设置里的默认方式打开（`openWith`），不弹菜单。
- 滚动/缩放/点击外部 → 关闭。

### 12.2 走查探针怎么写

- 放在 `tools/probe-*.js`，通过 `--ui-script` 注入页面执行。
- 脚本体是 `(async () => { ... })()`，可 `await`、末尾 `return 对象`，结果打到 stdout 的 `=== PRINTSHELF_UI_SCRIPT ===` 之间。
- 常用断言手段：
  - DOM 结构 / 文案 / class
  - `getComputedStyle` 拿 z-index、opacity、背景色
  - `document.elementFromPoint(x, y)` 判断「这个按钮是不是真的在最上层、点得到」
  - 合成事件：`PointerEvent` / `MouseEvent` / `KeyboardEvent` / `DragEvent`（`new DataTransfer()` 可以塞真 `File`，用来复现 `types` 含 `Files` 的场景）
- **注意**：`window.shelf` 是 contextBridge 暴露的只读对象（`Object.isFrozen === true`），**不能在页面里打桩**。探针不要去点「会真启动切片软件」的按钮，否则测试会真的拉起外部程序。

**为什么单独有个 `drag-e2e.js`**：页面里 `new DragEvent(...)` 的合成事件不经过浏览器进程的拖放协商，
`effectAllowed`/`dropEffect` 不匹配时它照样能"成功"，所以只能测出 JS 逻辑、测不出真实投放。
它需要 `--remote-debugging-port` + CDP 的 `Input.setInterceptDrags` / `Input.dispatchDragEvent`，
所以是独立的 Node 脚本，而不是 `--ui-script` 探针。跑之前会先把库复制到临时目录，不碰真实数据。

现有探针：

| 脚本 | 验什么 |
| --- | --- |
| `probe-devices.js` | 设备页渲染、两台在线、推送计数 > 0 |
| `probe-settings.js` | 设置页 5 区块、预设保护、文件关联 |
| `probe-u1-open.js` | 快造打开链路 |
| `probe-interactions.js` | 长按编辑模式、多选、Esc 退出、悬停二选一、库内拖动不误弹导入、设备页确认框可点 |
| `probe-sidebar.js` | 展开/收起状态、折叠态无残留文字、横向无溢出、title/aria 同步、grid 过渡、深色+列表叠加、浮层下可切、窄屏抽屉按钮可点 |
| `probe-boot.js` | 启动动画出现→结束→节点移除、CSS 12s 兜底、后端闸门存在、主界面已渲染、`finishBoot`/`bootFailed` 重复调用幂等 |
| `probe-perf.js` | 轻量刷新 0 查库 IPC、全量重建 vs 增量 patch 耗时、DOM 节点复用、滚动位置保留 |
| `probe-weblinks.js` | 两个导航按钮的 URL / 位置 / 可见可点性、勾选态不重叠、深色与窄屏适配；**不真的点击**（避免拉起浏览器） |
| `drag-e2e.js` | **真实拖放**：CDP 拦截真拖拽 → 派发 dragEnter/dragOver/drop → 校验 categoryId 真的落库（`npm run test:drag`） |

**探针不许污染用户设置（踩过坑）**：`--capture` 走真实 `data/`，点侧栏/主题/视图/排序按钮都会写 `settings.json`。
`toggleSidebar()` 里的 `settingsUpdate` 是 fire-and-forget，而 capture 在脚本返回后很快 `app.exit()`，
最后一次写入可能来不及落盘，导致用户下次打开软件侧栏莫名其妙变成折叠。

约定（见 `probe-sidebar.js` / `probe-perf.js`）：

1. 脚本开头 `await window.shelf.settings()` 快照整份 `ui`；
2. 结尾先把 DOM 点回原状态；
3. 再 `await window.shelf.settingsUpdate({ ui: originalUi })` **显式写回并等落盘** —— 这条排在写队列最后，能覆盖前面所有异步写入；
4. 把 `settingsRestored` 写进 `ok` 断言，别让「探针跑绿了但设置被改了」混过去。

**也不要用固定 `sleep` 等异步刷新**：`doRefresh()` 要跑 `query + stats + smartCounts`，冷启动或连续跑探针时
可能超过 800ms，固定等待会读到上一步的结果（表现为 `fullRender` 显示 `patch`、`patchRender` 显示 `full` 的假失败）。
`probe-perf.js` 改成轮询 `window.__printshelfRender.full / patch` 递增后再取 `lastMs/lastMode/replaced` 快照，
把 `settled` 写进 `ok`；连跑三次稳定（full 约 68ms / patch 约 1ms）。

## 14. 已知陷阱清单（改代码前扫一眼）

1. **`window.shelf` 只读**：不能打桩，测试别点会拉起外部程序的按钮。
2. **IPC 三处同步**：`ipc/index.js` / `preload.js` / `api.js`，漏一处就是「方法不存在」。
3. **事件白名单**：新推送不加 `preload.EVENTS` 就是静默失效。
4. **`dataTransfer.types` 含 `Files` 不等于外部拖入**：先看有没有 `application/x-shelf-ids`，再看 `.drag-holding-card`。
4b. **`dropEffect` 必须是 `effectAllowed` 允许的值**：不符时 `drop` 不触发，但 `dragover` 照常跑（高亮会有，像已经支持了）。
5. **`.card-media` 有 `overflow:hidden`**：任何要溢出卡片的浮层都得挂 `body`。
6. **`deviceWidth`/`aspect-ratio` 循环依赖**：`.card-img` 必须绝对定位，否则卡片高度塌成 0。
7. **主进程里不要同步递归扫盘**：会冻 UI（`findRelinkCandidates` 已改异步限时）。
8. **`before-quit` 要等落盘**：防抖中的写入否则会随退出丢失。
9. **写字符串到 `.js` 时注意转义**：曾用脚本写入含 `\n` 的中文导致字符串断行，`node --check` 直接报错；脚本改完立刻跑语法哨兵。
10. **测试数据隔离**：跑测试/走查不要写进用户真实 `data/`（`u1-cache` 曾被测试污染 54MB）。
11. **改折叠只走 `applySidebar()`**：直接改 `body` class 或 `state.sidebarCollapsed` 会让设置页开关、`title`、`aria-expanded` 与磁盘偏好互相打架（见 A.2）。
12. **加卡片可见字段必须同步 `cardSig()`**：指纹里没列的字段变了，增量渲染会认为"没变"从而不重画那张卡（见 A.3）。
13. **特殊视图整块替换 `#content`**：进 `duplicates` / `missing` 前必须 `invalidateGridCache()`，否则切回网格会对着别人的 DOM 做 `replaceChild()`。
14. **`window.shelf` 冻结，IPC 计数别在页面里打桩**：计数由 `api.js` 代理自己维护，读 `window.__printshelfIpc`。
15. **探针会写真实设置**：侧栏/主题/视图/排序按钮都持久化，探针结尾必须显式 `await settingsUpdate({ui: 快照})`，见 §12.2。
16. **后端没就绪别调 `api.bootstrap()`**：窗口现在先于 `services.init()` 创建，一律等 `whenBackendReady()`（见 §2.4）。
17. **缩略图 immutable 缓存依赖"文件名即内容哈希"**：若以后改成按 id 命名，必须撤掉 `max-age=31536000, immutable`，否则改图不刷新。
18. **库记录变少不一定是数据丢失**：监控目录里的 3mf 被外部删掉时，扫描会同步移除索引，这是正确行为；先核对磁盘文件是否真的不在了，别急着回滚备份（见 §12.3）。
19. **导航链接不要用 `<a href>`**：`app://` 页面被导航走会变成空白窗口，CSP 也只放行 `script-src 'self'`；一律 `button[data-url]` + `api.openExternal()`。
20. **颜色数组必须保留槽位下标**：`filament_colour` 里的空串/非法值要在原位留 `null`，不能压缩掉，否则 `filament_type` 会跟颜色错位、显示错误耗材类型。
21. **`filament_colour` 是 AMS 槽位配置，不是「模型用到的颜色」**：必须按 `model_settings.config` 每个零件的 `extruder`（1-based）映射才知道实际用了几色；`extruder=0` 是「跟随默认」，按槽位 1 处理。样本里 8 个槽位色但所有零件 `extruder=1` 的情况很常见。
22. **颜色回填只合并颜色字段**：`parse3mf(..., {withThumbnail:false})` 会把 `hasThumbnail`/`objectCount` 降级，整体赋回 `rec.meta` 会打坏已有数据；解析失败也要写空数组做「已处理」标记，否则每次启动都重试坏文件。
23. **色值进 `style` 前必须在渲染层再校验一次**：库可以被导入的 JSON 覆盖，`grid.js` 只接受 `/^#[0-9a-fA-F]{6}$/`，别把外部字符串拼进 `background:`。
24. **色板是异步回填后才出现的**：正常启动不阻塞首屏，写完库会触发一次 `lib:changed` 刷新；`cardSig()` 里必须有颜色字段，否则这次刷新会被增量渲染判成「没变」而不重画卡片（见 A.9）。
25. **改图标不要手改 `index.html`**：内联 sprite 由 `tools/icons/apply-sprite.js` 幂等安装，手工改的 `<symbol>` 会在下次重跑生成器时被整块覆盖；要换路径就改 `tools/icons/map.json`，再走 A.10.2 的流程（生成器 → sprite 片段 → 安装器）。
26. **两套 sprite 必须用同一组 `i-*` id**：`sprite-lucide.html` 与 `sprite-legacy.html` 只换 `<symbol>` 的**内容**、不换 id，`index.html` 里静态 46 处 `<use href="#i-*">` 与 `icon()` 才都不用改；id 一旦不一致，静态引用与 `icon()` 两边都要跟着改，也就不再需要「前缀映射」或常驻 `MutationObserver`（见 A.10.2 / A.10.3）。
27. **`motion.css` 必须是最后一张样式表，且所有简洁化规则以 `html[data-iconset="lucide"]` 开头**：顺序颠倒就盖不过 `components.css` / `layout.css` 的基础样式；漏前缀则切到 `legacy` 时简洁化规则仍生效，`legacy + off` 这个总回退就不再是「改造前界面」（见 A.10.3 / A.10.5）。
28. **卡片 hover 的覆盖规则必须限定 `.content-grid`**：列表模式靠 `#content.content-list .card { transform:none }` 禁位移，不限定作用域的 hover 规则会把它盖掉，列表里卡片又跟着抬起来（见 A.10.5）。
29. **`startViewTransition` 的回调是异步的**：不能包住需要在本次刷新里同步完成的轻量刷新，转场只包 `VIEW_TRANSITION_REASONS = viewmode / view / smartview` 三个 reason（`viewmode` 虽属 UI-only、仍不查库，但是用户可见的视图切换）；`UI_ONLY_REASONS` 里其余 reason 一律不包，卡片数超过 `MAX_VT_CARDS=150` 也直接跳过（见 A.10.4）。
30. **`.card-colors` 的 `position` / `transform` 不能被简洁化规则碰**：色板 hover 上移 30px、列表模式 `position:static; transform:none` 在 `probe-colors.js` 里都有断言，改了会直接挂既有探针（见 A.9 / A.10.5）。
31. **截图/走查不能改用户偏好**：`--ui=<场景>` 会点真实的 `#view-switch` 按钮，而 `toolbar.js` 把 `ui.view` 写进 `settings.json`；`runCapture()` 必须保留「进函数时快照整份 `ui` → `finally` 里 `store.updateSettings({ui: 快照})` 写回」。同理所有新探针都要用内存强制 + 逐项还原，或照 §12.2 做整份 `ui` 快照写回（见 A.10.7）。
32. **自动分类只填空 `categoryId`**：任何「顺手覆盖已有分类」的改动都会毁掉人工结果。`applyToRecord()` 第一行就是 `if (!rec || rec.categoryId) return null;`，扫描与批量两条路径都靠它兜底；要加新规则就只加关键词，别改这条判断。
33. **批量分类前必须干跑一次**：只要库里留着一个永远匹配不上的未分类文件，不干跑就会每次启动白写一次 `library.json`。`classifyUncategorized()` 先只读统计 `pending`，再干跑 `wouldAssign`，两者都为 0 时直接返回、不调 `updateLibrary`（见 A.11.5）。
34. **新增卡片可见字段要进 `cardSig()`**（与分类底色相关：`--cat-color` 已在指纹里），改卡片底色/分类色时别只改 CSS。只改 `components.css` 而不动指纹，增量渲染会判定「没变」，已渲染的卡片不会重画（与陷阱 12/24 同一类）。
35. **打印通知不要按「60 秒统一冷却」去重**：打完立刻报错、打印中先断料再报错都是真正需要各提醒一次的连续事件。正确规则是「同一任务同一类型永不重复」+「同类型不同任务才用 60 秒冷却压抖动」，见 `core/monitor.js` 的 `_checkNotify()`；单测里有专门断言。
36. **事件白名单要查「有没有人订阅」，不只是「有没有放行」**：`watcher:changed` 曾经主进程在推、preload 也放行，但 `api.js` 没转发，等于静默失效。`tools/check-ipc-contract.js` 会把 `preload.EVENTS` 与 `api.js` 的 `on(...)` 逐一比对；新增事件后跑一次，别只看方法表。

## 附录 A · 侧栏 / 性能 / 启动动画（2026-11-14）

三项改动各自的落点、时序边界与验证方式。改任何一处之前先读对应小节。

### A.1 启动加载动画与后端就绪闸门

| 环节 | 文件 | 关键点 |
| --- | --- | --- |
| 首帧画面 | `src/renderer/index.html` `<head>` 内联 `<style>` | `#boot-splash` 的 CSS 必须内联：外部 CSS/JS 还没加载时就要有东西；只用 `transform/opacity`，`pointer-events:none` |
| 动画骨架 | 同文件 `<body>` 顶部 `#boot-splash` | 环形 loader + 标题 + 进度条 + `#boot-hint`；`role="status"` `aria-live="polite"` |
| 纯 CSS 兜底 | 内联 CSS | `animation: boot-autohide .01s linear 12s forwards` —— 连 JS 都没加载成功也不会永久盖住界面 |
| 收尾控制器 | `js/components/boot.js` | `finishBoot(reason='ready')` / `bootFailed(reason='error')` / `bootStatus()` |
| 后端信号 | `electron/main.js` → `preload.js` → `js/api.js` | `app:ready` → `shelf.whenReady()` → `whenBackendReady()`（8 秒兜底 `Promise.race`） |
| 放行点 | `js/app.js` | `DOMContentLoaded` 后先等闸门再 `init()`；`bootstrap()` 开头再等一次 |
| 结束点 | `js/app.js` `runRefresh()` 的 `finally` | 第一轮界面真正画完 → `finishBoot('ready')`；`init`/`bootstrap` 抛错 → `bootFailed('mount'/'bootstrap')` |

`boot.js` 常量：`FADE_MS=280`、`HARD_TIMEOUT_MS=12000`、`MIN_VISIBLE_MS=460`。
`finish()` 用 `finished` 占位保证 ready / error / timeout / pagehide **只有第一次生效**；
`bootFailed()` 开头 `if (finished) return;` 保证「先 ready、后异步报错」不会重排定时器或改掉结束原因。
淡出移除靠 `transitionend`，另加 `FADE_MS + 90` 定时器兜底（减少动效 / 窗口遮挡时 `transitionend` 可能不触发）。

**四条收尾路径**：首轮渲染完成 → `ready`；挂载/启动抛错 → 先给中文提示、留约 900ms → `error`；12 秒硬超时 → `timeout`；JS 完全没跑 → 纯 CSS 12 秒自动隐藏。
**不阻塞启动**：没有同步等待，动画层不接收指针事件，卸载后不保留定时器或监听器。

### A.2 侧栏折叠：状态单一入口

`components/sidebar-state.js` 是**唯一**允许改折叠状态的地方：

```
applySidebar(collapsed, { persist = false })
  ├─ body.classList.toggle('sidebar-collapsed', on)      ← 所有 CSS 靠它
  ├─ setState({ sidebarCollapsed, settings.ui.sidebarCollapsed }, 'sidebar')
  ├─ #sidebar-toggle 的 title / aria-expanded
  └─ persist 时 api.settingsUpdate({ ui: { sidebarCollapsed: on } })
toggleSidebar() = applySidebar(!state.sidebarCollapsed, { persist: true })
```

调用方只有三处：`app.js` 启动时 `applySidebar(!!ui.sidebarCollapsed)`（不持久化，读磁盘偏好）、
切换按钮的 `toggleSidebar()`（持久化）、`views/settings.js` 的 `applyUI('sidebarCollapsed')` → `applySidebar(value)`。

修掉的四个真实缺陷：
1. 折叠后 `.nav-count` 等数字徽标仍可见 —— 旧 CSS 用「直接孙级」选择器，漏了 `.nav-sub` 包一层的情况；改成按类名精确隐藏（§11.5）。
2. 状态不同步 —— 以前 `app.js` 与 `settings.js` 各改各的，`title` 永远是「收起侧栏」、`aria-expanded` 为 null、设置页开关与实际状态打架。
3. 没有动画 —— `#body` 现在对 `grid-template-columns` 做 `var(--t-slow)` 过渡。
4. 窄屏收起后按钮滑出视口，无法再展开 —— `body.sidebar-collapsed .sidebar-toggle { position:fixed; left:4px; }`。

顺带修 `--card-size` 写错变量名：设置页 `applyCardSize()` 现在写的是网格真正使用的 `--card-w`。

验证：`node launch.js --capture=out.png --ui-script=tools/probe-sidebar.js`，
窄屏加 `--width=720`；断言含折叠 56px、`visibleTexts` 为空、`scrollOverflowX<=1`、title/aria、`transitionProperty` 含 `grid-template-columns`、抽屉 `left=-232`、按钮 `left=4`、`restoredCollapsed/settingsRestored`。

### A.3 性能：刷新调度、增量渲染、缓存

**① 刷新单飞与 UI-only 轻量刷新（`js/app.js`）**

`shelf:refresh` → `scheduleRefresh(reason)`：16ms 合并窗口（用 `setTimeout` 而非 `requestAnimationFrame`，后台/遮挡窗口里 rAF 会被暂停）、`refreshRunning` 单飞、`refreshAgain` 合并重入。
`pendingHeavy` 的规则是「合并窗口里只要有一个需要查库的原因，本轮就跑完整刷新」，避免数据刷新被 UI 刷新吞掉。

`UI_ONLY_REASONS = { viewmode, settings, theme, sidebar, cardSize, selection }` → `doLightRefresh()`：
`applyViewClass / renderSidebar / syncToolbar / syncBulkbar / renderStats / updateEmptyState / updateStatusBar`，
**不调 `api.query/stats/smartCounts`，不重建卡片**。
`views/toolbar.js` 切网格/列表发的 reason 是 `viewmode`（不是 `view`）；写错就会退化成整库重查。

**② 网格增量渲染（`js/views/grid.js`）**

`cardSig(m)` 列出 `cardHtml()` 真正读到的所有字段（含分类名、收藏、评分、meta 计数），逐卡比指纹：
- `canPatch` = 视图 className 未变 + 卡片数一致 + 非空；
- `diff.length <= items.length / 2` → 逐卡 `replaceChild()`；否则一次 `replaceChildren()`（换排序/筛选时逐张反而更贵）；
- 勾选态**不写进 HTML**，由 `syncSelectionDom()` 单独 classList.toggle，勾一张卡不再触发全网格重建；
- 全量重建时保存并恢复 `content.scrollTop`。

**③ 其他热点**

- `views/sidebar.js` `lastNavSig`：状态签名相同且 `lib.children.length` 非空就跳过 HTML 重建；签名含 `stats.totalSize / stats.thumbnails`；`flashCategory` 只作一次性强制重渲染条件、不写进签名。
- `app.js` `renderStats()` 的 `lastStatsSig` 缓存。
- `electron/main.js` `fileResponse(file, cacheControl)`；`shelf://thumbs/*` 返回 `Cache-Control: public, max-age=31536000, immutable` —— 文件名是内容哈希，复用 DOM 时不再重复读盘/解码。
- `main.js` `schedulePresetCheck()`：U1 预设体检延到 `signalRendererReady()` 之后、判 `services.initialized`，不占用启动关键路径。

**④ 边界：特殊视图**

`duplicates.js` / `missing` 会整块替换 `#content`。`app.js` 在该分支先 `invalidateGridCache()` 再 `renderSpecialView(mode)`；
`grid.js` 导出 `invalidateGridCache()` 清空 `lastRender`，否则切回普通网格会对着特殊视图的 DOM 做增量替换。

### A.6 三项为什么互不冲突

- **启动动画 vs 交互**：动画层 `z-index:9999` 但 `pointer-events:none`，不接收点击；只在 `runRefresh()` 的 `finally` 里删自己的节点，不碰 `#content`。
- **侧栏 vs 性能**：`applySidebar()` 用 reason `'sidebar'` 发刷新，落在 `UI_ONLY_REASONS` 里走轻量路径；`applyViewClass()` 只改 `#content.className`，不改卡片，也不破坏 `lastRender.cls`。
- **性能 vs 启动动画**：`renderGrid()` 的增量路径只做 `replaceChild()` / 跳过，首屏仍然由第一轮 `doRefresh()` 完整画出；`finishBoot()` 挂在 `runRefresh()` 的 `finally`，无论走 heavy 还是 light 路径都会收尾。
- **性能 vs 特殊视图**：用 `invalidateGridCache()` 明确切断 DOM 复用，避免两类视图互相污染。

### A.9 缩略图耗材色板（2026-11-14 晚）

需求原话：「这些模型的零件我想在缩略图看到有什么颜色可不可以看，不用点进去看」。
结论：在卡片 `.card-media` 右下角常显一排颜色圆点，数据直接从 3MF 里读，不点详情、不开切片软件。

#### A.9.1 数据从哪来（口径最容易搞错的一步）

| 文件（3MF 内） | 提供什么 | 注意 |
| --- | --- | --- |
| `Metadata/project_settings.config`（JSON） | `filament_colour`（或 `filament_multi_colour` / `default_filament_colour`）槽位色、`filament_type` 槽位耗材类型 | 这是 **AMS 槽位配置**，不代表每个槽都被模型用到；`extruder_colour` 是打印机机身色，**不能**当耗材色 |
| `Metadata/model_settings.config`（XML） | 每个 `<object>` / `<part>` 的 `<metadata key="extruder" value="N"/>`、对象级 `<metadata face_count="N"/>` | 真实样本属性顺序是 `key` 在前、`value` 在后；早先只匹配 `extruder="N"`，等于从没读到，`hasMultiColor` 一直 false |
| `Metadata/slice_info.config` / G-code | 逐色 `used_g`（`filamentUsages`） | 有就按克数算占比；未切片/没有逐色用量时为空 |
| `Metadata/filament_sequence.json` | 换色序列长度、盘子数 | 只用于 `filamentCount`，不参与选色 |

`src/core/model3mf.js` 的流程：

```
normalizeColor()              各种色值 → 安全 #RRGGBB（拒绝任意字符串）
firstColorArray()             选第一个有效颜色键，保留槽位下标（无效项为 null）
model_settings.config 解析     收集 extruder 索引；0 → 槽位 1，越界丢弃
colorPairs(allColors, allTypes, uniqIdx)
  ├─ 有 extruder → 按槽位取色，去重、最多 16 个，colorSource='objects'
  └─ 没有       → 退回全部配置色，           colorSource='project'
没有 filamentUsages 时，按 object extruder + face_count 聚合出 filamentFaceCounts
emptyMeta() 新增 filamentColors / filamentTypes / colorSource / filamentFaceCounts
hasMultiColor 一并校准为「实际颜色数 > 1 或多槽位」
```

`colorSource` 会进 tooltip：`objects` 写「零件用到的耗材颜色」，
`project` 写「切片配置中的耗材颜色（未找到零件挤出机映射）」，避免把配置色说成已用色。

- **幂等**：`apply-sprite.js` 可反复跑，每次都从 `tools/icons/` 的源片段重新生成，不累积差异；`sprite-legacy.html` 是一次性备份，之后不再被覆盖。因此**不要手改 `index.html` 的 sprite**（陷阱 25），下次重跑会被整块替换。

- `i-wrench` / `i-gear` 是本次补齐的两个缺失图标（设置页两个按钮曾空白）；`i-close` / `i-x` 按 `map.json` 都映射到官方 `x`，是**两个独立 symbol、路径相同**，不做去重合并。
- `i-globe`（官方 `globe`）是卡片悬浮条上的「打开来源网页」按钮。旧的眼睛按钮（`i-eye` / 大图预览）已换成它；大图预览仍可从右键菜单、键盘 `Space`、双击卡片进入。`legacy` 档没有这个自绘图，`apply-sprite.js` 会用 Lucide 路径补齐（缺失即补，不报错）。
- 新增图标的流程：改 `tools/icons/build-sprite.js` 的 `MAP`（它才是映射源，`map.json` 是它写出的产物）→ 跑 `build-sprite.js` → 跑 `apply-sprite.js` → 跑 `probe-icons.js`。别只改 `map.json`，下次生成会被覆盖。

| 开关 | 取值 | 默认 | 作用 |

**`legacy + off` = 改造前界面**：图标回到自绘路径、所有新增动效与简洁化规则短路。两个开关都走既有
`settingsUpdate` 链路 —— `store.js` 的 `mergeSettings` 对 `ui.*` **没有字段白名单**，任意 `ui.*` 键都会被
合并并落盘，所以**不新增 IPC**，旧 `settings.json` 缺字段时由默认值补齐、不需要数据迁移。

#### A.10.4 动效档位判定与降级链

- 用户档位 `ui.motionLevel`：`full` / `reduced` / `off`；`prefersReducedMotion()` 读系统「减少动态效果」。
- **2026-11-19 修订：系统偏好不再硬覆盖应用档位。** 默认 `ui.motionFollowSystem = false`，
  `effectiveLevel()` 直接返回 `motionLevel`（`full` 就是 `full`）；只有用户打开「跟随系统」
  且系统命中 reduce 时才降为 `reduced`。`off` 永远一票否决。
  原因：系统开关只是建议，游戏与多数桌面软件都不跟随；硬覆盖会让用户「选了完整却没动效」，
  看起来像 bug。需要无障碍降级的用户有显式开关。
- `base.css` 的全局限动规则同样是**属性驱动**的：`html:not([data-motion-effective="full"]) * { ... }`。
  只改 JS 档位、不改这条，CSS 时长仍会被 `@media (prefers-reduced-motion)` 压成 `.001ms`。
- `reduced` 档额外放行「非位移」过渡（透明度/颜色/背景/边框/阴影 150ms），位移类仍为瞬间；
  否则开了系统限动的机器上所有反馈都是硬切，反而看不清状态变化。
- `reduced` 只保留**纯 opacity 淡入**，不做位移、不做 View Transitions、不做循环动画；
  `off` 时无 View Transition、无新增 keyframes，`getComputedStyle(...).animationName === 'none'`。
- `motionEnabled(level)` 是所有新增动效调用点的短路入口；`EASE` 从 `--ease-ui` 读取，兜底 `cubic-bezier(.2, .7, .3, 1)`。

`withViewTransition(reason, callback)` 的 **5 条降级路径**（命中任一条 → 直接 `callback()`，不包转场，
并把原因记进 `vtFallback`）：

| # | 条件 | 处理 |
| --- | --- | --- |
| 1 | `ui.motionLevel === 'off'`（或 `effectiveLevel === 'off'`） | 直接更新 |
| 2 | `effectiveLevel === 'reduced'` | 直接更新（reduced 不做转场） |
| 3 | `reason ∉ VIEW_TRANSITION_REASONS` | 直接更新；白名单只有 `viewmode` / `view` / `smartview` |
| 4 | `document.startViewTransition` 不存在 | 直接更新（不支持该特性） |
| 5 | 卡片数 > `MAX_VT_CARDS`（150） | 直接更新，避免 `#content` 几百张卡全量快照掉帧 |

`UI_ONLY_REASONS = ['viewmode','settings','theme','sidebar','cardSize','selection']` **未变**，这些轻量刷新
不查库、必须在本次刷新里同步完成，不能包进异步的转场回调（陷阱 29）；`VIEW_TRANSITION_REASONS` 是新增的
转场白名单。其余约定：`#view-title { view-transition-name: shelf-title; }` 只给标题命名，不给每张卡片命名；
`::view-transition { pointer-events:none; }` 防转场期间拦截点击。

#### A.10.5 视觉「去堆砌」做了什么，以及为什么规则必须带 iconset 前缀

按 Q1 覆写后的「高雅、克制、不堆砌」，本轮只做减法：

- 卡片 hover 从「位移 + 工具条滑入 + 色板上移 + check/fav/badges 淡出」多层同时变化，收敛为
  **「主位移 1 次 + 工具条 1 次」**；去掉同帧多余的 opacity 抖动、过密分割线与重复徽标。
- 覆盖规则**限定在 `.content-grid`**（陷阱 28），列表模式 `transform:none` 才不会被盖掉；
  统一 `:focus-visible`，hover 不再是唯一可达路径。
- 按钮 `:active` 用 `--dur-tap`(80ms) 的短下压；状态反馈走一次性 WAAPI 脉冲，不触发额外查库。
- **不新建骨架屏、不新建全局遮罩**（S4 按「不堆砌」缩减，见 A.10.8 b）；
  **`.card-colors` 的 `position` / `transform` 一律不动**（陷阱 30，`probe-colors.js` 有断言）。
- `--ease` 保持 `ease` 不动，只新增令牌（A.10.8 f），既有 56 条 transition 不受影响。

**为什么所有简洁化规则必须以 `html[data-iconset="lucide"]` 开头**：这些规则是「配合 Lucide 统一笔触」
才成立的视觉调整，属于新界面的一部分，不属于改造前界面。总回退要求 `legacy + off` 精确等价于改造前；
若规则不带前缀，切到 `legacy` 后它们仍生效，回退就「退不干净」。同理动效规则以
`html[data-motion-effective]` 开头；而 `motion.css` 必须排在**最后一张**，这些带前缀的覆盖规则才盖得过
`components.css` / `layout.css` 的基础样式 —— 顺序一颠倒或前缀一漏，回退与简洁化会同时失效（陷阱 27）。

### A.11 预设词库自动分类（2026-11-15）

#### A.11.2 数据模型

```js
settings.classify = {
  enabled: true,          // 总开关；false 时扫描与启动都不跑（手动「立即分类」可 force 绕过）
  onScan: true,           // 新导入 / 扫描时即时匹配
  onStartup: true,        // 每次启动补一次未分类
  rules: [                // 空数组 = 还没生成过，运行时回落到内置预设
    { id: 'rule_test', categoryId: 'cat_xxx', keywords: ['测试', '校准'] },
  ],
  lastRunAt: 0,           // 上次「真的分到东西」的时间
  lastRunStat: { scanned: 134, assigned: 4, skipped: 130 } | null,
}
```

- 存盘的规则只有三件套 `{ id, categoryId, keywords[] }`。`DEFAULT_RULES` 里的 `categoryNames` 只是生成期的锚点，**不会**写进设置。
- 记录侧新增可选字段 `autoClassified?: boolean`：`true` = 这条分类是自动写的；`false`/缺省 = 人工或尚未分类。它不在 `library.js` 的 `UPDATABLE_FIELDS` 里，渲染层不能通过 `api.update()` 直接改。
- `configOf()` 负责补齐默认值，所以旧 `settings.json` 没有 `classify` 组也能直接跑，不需要数据迁移。

#### A.11.3 匹配算法

```
haystack = [
  title, fileName, author, note, sourceUrl,
  dirsOf(relativePath), dirsOf(path),        // 父两级目录（跳过文件名）
  meta.objNames.join(' '),                   // 3MF 内部对象名，最多 12 个
].filter(非空).join(' ').toLowerCase()

for (rule of rules) {                        // 数组顺序即优先级
  if (!rule.categoryId) continue;
  for (kw of rule.keywords) {
    if (kw.trim().toLowerCase().length < 2) continue;   // 单字误伤太大
    if (haystack.includes(kw)) return rule.categoryId;   // 第一条命中即止
  }
}
return null;                                 // 不做兜底
```

- `dirsOf()` 取路径最后两级的**目录名**（不含文件名）；盘符和用户目录太长、区分度低，不参与匹配。
- 关键词统一小写比较；中文不受影响，`Benchy` / `benchy` 等价。
- **不做兜底**：不命中就保持未分类。全塞进「摆件装饰」会让「还有哪些没分」的信号消失。
- **批量**写库前还会再查一次 `categoryId` 是否仍存在于当前分类表；分类刚被删掉时不写无效 id（见 A.11.6）。扫描即时匹配不查这一层。

#### A.11.4 预设词库与分类名锚定

`DEFAULT_RULES` 的顺序固定为 **测试校准 → 备件维修 → 功能件 → 唱片/绘画 → 摆件装饰**。每条规则带一个 `categoryNames` 候选列表，`presetRules(categories)` 按候选顺序找第一个存在的分类名，解析成 `categoryId`：

| 规则 | `categoryNames` 候选（从左往右取第一个存在的） | 关键词数 |
| --- | --- | --- |
| `rule_test` 测试校准 | 测试校准 / 测试 / 校准 | 15 |
| `rule_part` 备件维修 | 备件维修 / 备件 / 维修 | 15 |
| `rule_func` 功能件 | 功能件 / 功能 / 工具 | 21 |
| `rule_disc` 唱片/绘画 | 唱片/绘画 / 唱片与音频 / 唱片 / 绘画 | 13 |
| `rule_deco` 摆件装饰 | 摆件装饰 / 摆件 / 装饰 | 39 |

- **首次生成**：`settings.classify.rules` 为空时，`resolveRules()` 运行时回落到 `presetRules()`；设置页首次打开「自动分类」tab 时也会调 `ensureClassifyRules()`，把解析结果写进 `settings.classify.rules` 落盘。之后**以用户编辑后的为准**，不再自动覆盖。
- **分类被删则跳过**：候选名一个都不存在时，这条规则不生成（不报错）；设置页对应规则行显示「分类已删除（规则暂停）」。用户新建同名分类后点「恢复预设词库」即可补回。
- **恢复预设词库**：`api.classifyPreset()` → `presetRules(当前分类)` → `settingsUpdate({ classify: { rules: 预设 } })`。只重建词库，**不回改历史分类**。
- 用户给分类改名不影响已生成的规则（规则绑的是稳定的 `categoryId`）；但改名后「恢复预设」会按新名字重新锚定，找不到就跳过该条。

#### A.11.5 三个触发时机与性能

| 时机 | 入口 | 行为 |
| --- | --- | --- |
| 扫描（新导入 / 变更文件） | `scanner.js` `_run()` 的并发 `worker(item)` 回调 | 整轮只读一次配置与规则；记录组装完、`categoryId` 兜底为 `null` 后就地匹配，命中即写 `categoryId + autoClassified`，`report.autoClassified` 累加。**不是独立线程**，只是扫描的并发 worker 函数 |
| 应用启动 | `main.js` `scheduleAutoClassify()` | `signalRendererReady()` 之后延迟 **1.6s**，异步调 `classifyUncategorized()`；不 await、不阻塞首屏 |
| 设置页「立即分类未分类」 | `ipc` `classifyRun` → `classifyUncategorized(store, { force: true })` | `force` 忽略总开关；返回统计供 Toast 与「上次运行」文案使用 |

**干跑（写库前先算一遍）**，这是启动路径最关键的优化：

1. 先只读遍历：统计 `scanned / skipped / pending`。`pending === 0` 直接返回，**连 `updateLibrary` 都不调**。
2. 有未分类时再干跑一遍 `matchCategory()`，并检查命中的 id 是否还在当前分类表；`wouldAssign === 0` 也直接返回。
3. 只有确实能分到东西，才进 `store.updateLibrary(..., 'classify')`，整批一次写盘、一次 `lib:changed`。
4. `lastRunAt / lastRunStat` 也只在 `assigned > 0` 时写，避免每次启动都写 `settings.json`。

没有干跑时，只要库里留着一个永远匹配不上的未分类文件（比如无标题、无对象名的哈希文件），每次启动都会白写一次库（陷阱 33）。匹配本身是纯内存字符串比较，成本远低于写盘与一次界面刷新。

#### A.11.6 安全边界

| 风险 | 处理 |
| --- | --- |
| 覆盖人工分类 | `applyToRecord()` 只处理 `!rec.categoryId`；已有非空分类一律不动，空字符串等同未分类 |
| 误塞进某个分类 | 不命中就保持未分类，**不做兜底**；单字关键词直接忽略 |
| 撤销自动结果 | `undoAutoClassified()` 只清 `autoClassified === true` 的记录；先只读判断有没有可清的，没有就不写库 |
| 分类被删后写入无效 id | **批量分类**（启动 / 立即分类）写库前重新解析规则并取当前分类 id 集合；命中已删除分类时把 `categoryId` 置回 `null`、`autoClassified` 置 `false`。**扫描即时分类**只按 `settings.classify.rules` 匹配，不校验分类是否还在——删分类后请在设置页删掉该条规则或点「恢复预设词库」，否则新扫描仍可能写入旧 id |
| 用户不想用 | `enabled: false` 时扫描与启动都不跑；`onScan` / `onStartup` 可分别关。设置页「立即分类」用 `force: true`，是用户显式动作 |
| 词库改坏 | 编辑只影响后续匹配，不回改历史分类；「恢复预设词库」可重建默认规则 |

**一个已知边界**：人工把一条「自动分好的」卡片拖到别的分类时，`library.update()` 只改 `categoryId`，不会清 `autoClassified`；之后点「撤销自动分类」仍会把这条一起清空。要保留人工结果，就别在改过之后用全局撤销，直接手动再分一次即可。

### A.12 来源网页（3MF 项目信息里的作品链接）

**数据在哪**：Bambu Studio「项目信息」面板里那个可点的链接，存在 `3D/3dmodel.model` 的
`<metadata name="Description">` 里，是一段 HTML 富文本，而且常被实体转义两层：

```
&amp;lt;a href=&amp;quot;https://makerworld.com/es/models/3377037-soporte...&amp;quot;&amp;gt;点我&amp;lt;/a&amp;gt;
```

所以**用普通 URL 正则直接扫 3MF 是扫不到的**——`&amp;` 夹在 `https` 前面，正则一匹配就断。
早期版本正是因此判断「3MF 里没有链接」，实际是没解码。

**解析**（`src/core/model3mf.js`）

- `decodeEntities()` 解两次实体 → `extractSourceUrl()` 提取 URL → `isModelPage()` 判定。
- **只认作品页路径**：`makerworld.com[/zh|/es]/models/<id>`、`printables.com/model/<id>`、
  `thingiverse.com/thing:<id>`、`cults3d.com/<lang>/3d-model/...`、`myminifactory.com/object/<id>`、`thangs.com/models/...`。
- **明确排除**（都是 Description 里真实出现过的干扰项）：
  - 预览图 CDN：`makerworld.bblmw.cn/makerworld/model/DSM.../design/x.png`
  - 任何 `/design/` 路径、图片扩展名（`.png/.jpg/.gif/.webp/.svg`）
  - 作者主页：`makerworld.com/zh/@Evan76`
  - 工具页：`makerworld.com.cn/makerlab/chromaCanvas`
  - 坏拼接：`makerworld.com/%22https://www.instagram.com/...`（作者把 HTML 写坏了）
  - 尾部粘着 `\` `"` `` ` `` `<` `>` 的转义残留
- 找不到就返回 `null`，卡片上的地球按钮表现为「点了没反应」。

**写入与回填**

- 扫描时：`scanner.js` 在记录构造阶段读 `meta.sourceUrl`，**只在 `record.sourceUrl` 为空时填**，
  用户手填的一律不覆盖。
- 老记录：`src/core/source-urls.js` 的 `backfillSourceUrls()`，启动后 2.4s 跑（capture 模式下 await），
  并发 4、整批写一次库；没有可处理的记录时连库都不写。
- 自动填的值带 `sourceUrlAuto: true`。清理只针对「有标记 **且** 不是作品页」的旧值；
  用户手填的（没有标记）永远不动。

**实测（136 条）**

- 12 条解析出作品页链接（塞尔达笛 `models/3377037`、马里奥皇冠 `models/1752939`、
  A2L 拖链 `models/2909299`、cosplay 卡尺等），其余 3MF 里只有图片或根本没有作品地址。
- 第一版没有作品页判定，写进过 34 条错误值；标记为自动后按新规则清空并重解析，现在 12 条全部是干净的详情页。

**中国站（默认自动）**

MakerWorld 中国站（`makerworld.com.cn`）与国际站是**两套独立的模型库**，同一个作品的 ID 不一样。
实测 `makerworld.com/zh/models/3377037-...` 在中国站返回「模型不存在」；同名的国服页面是另一个作品

- `makerworld.com` → `makerworld.com.cn`。
- 语言段一起归一：`/en/`、`/es/`、`/zh-cn/` 都换成 `/zh/`；没有语言段的 `/models/...` 保持原样。
- 路径 / query / `#profileId` 全部保留；国服没同步的模型会显示「模型不存在」。

| 开关 | `openExternal` 行为 |
| --- | --- |
| 开（默认） | `cnMakerWorldUrl()` 换成 `makerworld.com.cn` 并归一 `/zh/`；路径 / query / `#profileId` 保留 |
| 关 | 原样打开记录里的 `sourceUrl`（国际站详情页） |

### A.13 机内摄像头与「打印机检测」

**协议（实测 2026-11-15，A1 系列 3DP-XXXX-XXX）**

拓竹 A1 / A1 mini / P1P / P1S 的机内摄像头走 **TCP 6000**，不是 MQTT，也不是 322 的 RTSP（A1 的 322 端口实测 `ECONNREFUSED`）：

1. TLS 连接 6000，证书自签 → `rejectUnauthorized: false`
2. 发 **80 字节鉴权包**：
   - `[0:4]` = `0x40`（payload 长度 64）
   - `[4:8]` = `0x3000`（消息类型）
   - `[8:16]` = 0
   - `[16:48]` = `"bblp"`（用户名，补齐 32 字节）
   - `[48:80]` = access code（访问码，补齐 32 字节）
   - **用户名在前、访问码在后**。写反打印机会直接关连接且不报错，表现为「连上了但一帧都不来」
3. 之后持续推帧：**16 字节头 + JPEG**，头 `[0:3]` 是 payload 长度（24 位小端），payload 以 `FFD8` 开头、`FFD9` 结尾
4. MQTT 里的 `{"camera":{"command":"start"}}` / `{"xcam":...}` 在这台机器上**都返回 `FAILURE`**，不要走那条路

**四个实测坑**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 鉴权后 0 字节 | 用户名/访问码偏移写反 | `bblp@16`、`code@48` |
| 第二个连接只收到 16 字节帧头 | 6000 同时只接受一个连接，断开后释放有延迟 | 全局串行队列 + 400ms 冷却 |
| 12 秒只到 1 帧 | 帧率低（约 3 秒一帧），且**第一帧是缓冲里的旧画面** | 默认**不跳**首帧；需要时显式 `skipFirst` |
| 倒计时到 0 还没图 | 抓两帧实际 10~14 秒 | 归零后文案变「处理中…」，不硬撑 10 秒 |

**文件与入口**

| 位置 | 作用 |
| --- | --- |
| `src/core/camera.js` | `buildAuthPacket()` / `captureSeries()` / `captureFrame()` / `captureTwo()`；串行队列 + 冷却 |
| `electron/ipc/index.js` | `cameraFrame(id)` 单帧、`cameraDetect(id)` 两帧（间隔 3 秒）；非拓竹设备直接报错 |
| `js/views/devices.js` | 卡片上的「摄像头」「打印机检测」按钮、画面区、检测三态 |
| `components.css` | `.dev-cam` / `.dev-cam-empty` / `.detect-grid` |

**交互**

- 「摄像头」：开 → 抓到一帧后**串行再排下一次**（不用 `setInterval`，否则请求越积越多）；再点一次关闭；关闭设备弹窗时全部停掉
- 「打印机检测」：点 → 按钮置灰、显示 `检测中 10s` 倒计时 → 抓两帧（间隔 3 秒）→ 变「查看图片」→ 点开弹窗并排看两张，提示重点看炒面 / 空打 / 翘边
- 检测结果保存在 `detectState`，可反复点开查看；重新检测覆盖

**验证**

```bash
node launch.js --capture=out.png --ui-script=tmp.js   # 打开设备 → 点摄像头 → 等 7s 读 .dev-cam img
node tools/syntax-check.js
```
实测：画面 `naturalWidth=1536`、单帧 144KB；检测按钮 `打印机检测 → 检测中 7s(disabled) → 查看图片`，弹窗两张图 `naturalWidth>0`。

## 附录 A.14 · 打印监控三项（2026-11-15）

### A.14.1 需求与取舍

用户在此前的问卷里把「常驻监控条 / 完成与异常通知 / 温度与进度曲线」都勾成了可选项，所以三项各自有独立开关（设置 → 打印监控），默认开启、互不依赖：

### A.14.4 常驻监控条

- 位置：`#monitor-bar` 插在 `#stats-bar` 与 `#scan-progress` 之间，`layout.css` 里与它们一起标 `flex: 0 0 auto`，不挤占 `#content` 的滚动区。
- 数据：`printersList()` 定顺序（含已配置但离线的设备补一条占位），`printersSnapshot()` 取首帧，之后全靠 `printers:update` 推送。
- **卡片级增量**：每张卡片带 `data-sig`（可见字段的 JSON），只有温度/进度/状态真的变了才 `outerHTML` 替换那一张。整条每 3 秒重建会打断 hover、也会让「曲线」按钮点不中。
- 20 秒兜底重拉一次快照，防 MQTT 长时间静默导致界面停在旧值。
- 点卡片 = 打开设备面板；点「曲线」= 该设备的历史；顶部「看曲线」= **全部设备里最近一次有记录的打印**（早期版本写死第一台，第一台常常空闲，点开永远是空态，已修）。
- 设置里改 `monitor.*` / `notify.*` 也会发一次 `emitRefresh('settings')`，监控条订阅 `shelf:refresh` 后立刻显隐，不用重开设置页。

### A.14.5 完成与异常通知

- 只认「在线 → 在线」的状态转移：`finished`（从 printing/paused/preparing 来）、`error`、`paused`（从 printing 来）。
- 首次见到一台设备**不补发**历史通知；`online:false` / `connecting` 中间态既不通知也不覆盖 `lastState`，避免 MQTT 重连重复弹「已完成」。
- 去重（陷阱 35）：同一任务同一类型只发一次；**不同类型之间不互相冷却**（打完立刻报错、先断料再报错都要各提醒一次）；同类型不同任务 60 秒内不重复，用来压 MQTT 抖动。
- 系统通知由 `main.js` 发（`app.setAppUserModelId` 已在启动时设好，Windows 才能正常显示），应用内 toast 由 `api.js` 发；`notify.system=false` 时只保留后者。设置页「发一条测试通知」走完全相同的出口。

### A.14.6 温度与进度曲线

- 采样点格式 `[t, percent, nozzleCur, nozzleTarget, bedCur, bedTarget]`，紧凑数组而不是对象：一次 7 小时打印约 1800 点，对象会多出十几倍体积。
- 一个打印任务 = 一个 session；任务名变化、或设备从活跃转空闲都自动收尾。每台最多 `MAX_POINTS=1800` 点（丢最旧的），全机最多 `monitor.keepSessions` 个 session。
- 双轴：左温度 0..`tempMax`（按峰值向上取整到 50℃，至少 100℃）、右进度 0..100%，横轴真实时间；四条线 = 喷嘴 / 喷嘴目标（虚线）/ 热床 / 进度。坐标与统计由 `buildChartModel()` 算好，渲染层只拼 `<svg>`，不复制第二套缩放算法。
- 弹窗内可下拉切换历史任务，下拉带**设备名**（多台同型号机器才分得清）。点数少于 3 个时明确提示「才刚开始记录」并把末端圆点放大，避免看起来像坏图。
- 落盘 `data/monitor/history.json`：`tmp + rename` 原子写；每 12 点 / 30 秒、任务结束、`shutdown()` 各 flush 一次；异常退出后重启会把还标着「进行中」的 session 补上 `endedAt`；文件损坏时静默重置为空，不影响启动。

### A.15.3 陷阱清单（改这里之前先看）

37. **回执事件不能被通知开关吞掉**：`_checkNotify()` 里 `notify.enabled` 的检查必须放在 `emit('job')` **之后**。早期版本把 `if (!notify.enabled) return` 放在函数开头，导致关通知的用户永远没有回执——单测里有专门断言。
38. **3MF 重量不是标配**：实测 133 个可读文件只有 25 个带重量。没有重量时 `weightG=null` 是**正常**，不要报错、不要硬塞 0；UI 显示「未取到」并让用户填。
39. **异常重量必须校验**：有过 `volume=9297cm³` 却 `weight=11.62g` 的矛盾文件。`isValidWeight()` 限定 `0.01 < w <= 5000`，越界一律丢弃。
40. **自动回写状态必须精确匹配**：`matchModel()` 去路径 / 扩展名 / `_U1_<hash>` 后缀后按小写比对，且**要求唯一命中**；多个同名或匹配不到都返回 null，宁可漏不可错——用户确认要自动改状态，误改比漏改更糟。
41. **耗材图片必须按内容哈希命名**：`shelf://filaments/` 与缩略图一样声明了 `immutable`；换图沿用旧文件名会让浏览器永远显示旧图。`setImage()` 已是「内容变 → 文件名变」。
42. **耗材图片路由要放在缩略图路由之前**：`main.js` 的 `protocol.handle('shelf')` 先判断 `/filaments/` 前缀，否则同名文件会串到 thumbs 目录。
43. **耗材写操作要推 `filaments:changed`**：渲染层把这个事件 → window 事件 → 面板自动 refresh。漏推时新建 / 改价后卡片不刷新，看起来像"保存没生效"（探针就是靠这个抓出来的）。
44. **详情成本区块是异步填充的**：`render()` 先放占位，`fillCost()` 取完成再只替换 `#detail-cost` 的 innerHTML；期间用户切到别的模型要用 `currentId` 判旧，别把 A 的成本画到 B 上。
45. **耗材数据不进备份**（用户确认）：`store` 的自动备份、`exportData` / `importData` 只管 `library.json`。换机迁移要单独拷 `filaments.json` / `receipts.json` / `filament-img/`。

`openSettings()` 原来只 `renderContent()`，读的是 `state.settings` 快照。正常用户路径没问题（`showClassifyPrompt()` 在跳过成功后会把 `skippedIds` 同步进 `state.settings`），但只要设置是**从别处**改的——另一个窗口、原生菜单、或探针直接走 IPC——面板就会显示旧状态，典型表现是「明明有跳过记录，但『恢复提醒』按钮不出现」。

对应陷阱 **53**：**别用 `state.settings` 当设置页的唯一真相源**。凡是有外部写入可能的面板，打开时都应 `api.settings()` refetch 一次；只靠内存快照会出现「数据对了、界面没对」的鬼影。

验证：`probe-classify-skipreset` 连跑两次 `ok:true`（假名单 2 条 → 按钮出现 → 二次确认 → 清空），且与 `probe-settings`、`probe-classify-skip` 互不影响。
