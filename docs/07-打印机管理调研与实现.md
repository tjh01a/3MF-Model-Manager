# 07 · 打印机管理（快造 U1 + 拓竹）调研与实现

> 2026-11-14。目标是「一个面板里看见两台机器在干什么」，不再为了看一眼进度去开两个切片软件。

## 一、结论

**可行，而且不需要任何第三方库。** 两台机器在局域网上都暴露了开放的通信接口，本工具直连读取，不和切片软件抢控制权。

| | 快造 U1 | 拓竹（3DP-26A-721） |
| --- | --- | --- |
| 地址 | `192.168.1.50` | `192.168.0.109` |
| 协议 | **Moonraker**（Klipper 的 HTTP API） | **MQTT over TLS** |
| 端口 | 7125（API）/ 80（Web）/ 8883 | 8883（MQTT）/ 990（FTPS）/ 6000（摄像头） |
| 认证 | **无**（局域网免认证） | 用户名固定 `bblp`，密码是屏幕上的 8 位访问码 |
| 读取方式 | `GET /printer/objects/query?…` | 订阅 `device/<序列号>/report`，发 `pushall` 要全量 |
| 控制 | `POST /printer/print/{pause,resume,cancel}` | 发布 `{"print":{"command":"pause"/"resume"/"stop"}}` |
| 实现 | 内置 `http` | 内置 `tls`，自己拼 MQTT 包 |

## 二、实测事实（不是文档抄的）

### 2.1 快造 U1

```json
GET http://192.168.1.50:7125/printer/info
{"result":{"state":"ready","hostname":"lava","software_version":"2.0.0.205_20260914173503"}}
```

打印中：
```
print_stats  : filename=组合体_PETG_12h19m.gcode, state=printing, print_duration=1983s
               info: {total_layer:625, current_layer:1}
virtual_sdcard: progress=0.00169, file_position=181296, file_size=107184704
heater_bed   : 70.03 / 70
extruder     : 245.0 / 245, extruder_index=0
print_task_config: filament_type=[PETG×4]
                   filament_color_rgba=[FFFFFFFF,39FF14FF,FEE5A5FF,000000FF]
                   filament_vendor=[Polymaker,Snapmaker,Snapmaker,Snapmaker]
```

**坑一：`virtual_sdcard.progress` 是字节进度，刚开始打印时几乎为 0。**
第 1/625 层时它只有 0.17%，直接显示会像「没动」。所以进度取 `max(字节进度, 当前层/总层)`。

**坑二：Klipper 不给 ETA。** 剩余时间靠两条路：
1. 快造导出的文件名自带时长（`xxx_PETG_12h19m.gcode`）→ 总时长 × (1 − 进度)，实测 738 分钟 = 打印机屏幕上的 12h18m；
2. 没有就按已打印时间反推，进度低于 2% 时宁可不显示，也不编数字。

**坑三：4 个工具头的温度在 `extruder` / `extruder1..3`。**
只查 `extruder` 是安全的；一次查不存在的对象会让整条 query 报错，所以主查询只带 `extruder`。

### 2.2 拓竹

证书是自签的，**CN 就是序列号**（形如 `03A00XXXXXXXXXX`），所以发现设备时顺带就能拿到序列号，不用让用户抄。

连上后不会自动推全量，要主动发 `{"pushing":{"sequence_id":"1","command":"pushall"}}`：

```
gcode_state  : RUNNING
subtask_name : 三角洲×影之刃-黑伤【联名刀皮】-A1(3)_刀鞘.3mf
mc_percent   : 24        mc_remaining_time: 357
layer_num    : 160 / 1000
nozzle_temper: 244.7 / 245     bed_temper: 70 / 70
```

**坑四：AMS 数据在 `print.ams` 里面，不在顶层。** 结构是 `print.ams.ams[0].tray[]`，每个 tray 是 `{id, tray_type, tray_color, …}`，颜色是 **RRGGBBAA**（快造给的也是这个顺序，不是 ARGB）。
`tray_now` 的位置不同固件不一样（AMS 单元上 / 每个 tray 上），代码里做了三级兜底。

**坑五：访问码可以直接从 Bambu Studio 的配置里读**，不用手抄：
`%APPDATA%\BambuStudio\BambuStudio.conf` → `"access_code": { "<序列号>": "<8位码>" }`。
发现设备时会自动带上；读不到就让用户手填。

## 三、统一模型

两个驱动都归一到同一个结构，界面只认这个：

```js
{
  id, kind: 'snapmaker'|'bambu', name, model, ip,
  online, state: 'idle'|'printing'|'paused'|'preparing'|'finished'|'error'|'offline',
  stateText,
  job: { name, percent, layer, layers, elapsedMin, remainingMin } | null,
  temps: { nozzle:{cur,target}, bed:{cur,target}, chamber:{cur,target}|null },
  materials: [{ slot, type, vendor, color, active }],
  fan, speed, updatedAt, error
}
```

## 四、实现要点

- **快造走轮询、拓竹走长连接**：Moonraker 没有推送，3 秒一次 HTTP；拓竹是 MQTT，连上就一直推，自己发 PINGREQ 保活。两者互不影响，一台掉线不拖累另一台。
- **偶发超时不判离线**：连续两次失败才标离线，避免热床波动时卡片乱闪。
- **自动发现**：扫本机 `/24` 网段，只探两个特征端口（7125 = Moonraker、8883 = 拓竹），并发 48、单个 420ms，整轮 2~4 秒。
- **控制要二次确认**：暂停/继续直接发；**停止必须弹确认**，并说明「打印件作废」。
- **零新增依赖**：MQTT 只用了 CONNECT / SUBSCRIBE / PUBLISH / PINGREQ 四种包，自己拼字节比引 `mqtt` 包更省心。

## 五、已知限制（写清楚，不装作没有）

1. **摄像头没接**。拓竹是 6000 端口的私有 JPEG 流（要访问码），快造是 Web 端。下一版再做。
2. **AMS 空托盘**：实测那台拓竹当前 `tray` 只有 `{id:"0"}…{id:"3"}`，没有耗材字段 —— 机器侧没上报，界面就显示「没有耗材信息」，不猜。
3. **不能发起打印**。上传 gcode 走 FTPS/HTTP，涉及文件写入，风险等级不同，单独评估。
4. 快造仍只支持局域网；**拓竹已补云端通道**（见下方「附 2」），但仅用于读取状态与控制，不做模型上传、不做库数据同步；快造云不碰。
5. 拓竹的 `elapsedMin` 目前留 0 —— 报文里没有可靠的已打印时长，不编。

## 附：2026-11-14 排查记录 · 拓竹 `ECONNREFUSED ...:8883`

**现象**：设备页拓竹显示「连接中」，错误行是 `connect ECONNREFUSED 192.168.0.109:8883`；同一时刻打印机确实在打印，Bambu Studio 也能看到画面。

**排查步骤与结论**（按这个顺序查，几分钟能定性）：

1. **端口是不是真的开着**
   ```bash
   node -e "const n=require('net');const s=n.connect(8883,'192.168.0.109',()=>{console.log('open');s.destroy()});s.on('error',e=>console.log(e.code))"
   ```
   结果 `ECONNREFUSED`；`ping` 通，但该 IP 的 MAC 已不是打印机 → **这个地址已经属于别的设备**（DHCP 换了）。

2. **扫网段找「谁开着拓竹的特征端口」**
   特征端口组合：`8883` MQTT / `6000` 摄像头 / `990` FTPS / `322` FTPS（旧机型）。
   实测 `192.168.0.108` 同时开着 6000、990、8883 → 打印机大概率搬到了 `.108`。
   `192.168.1.50` 的 8883 是快造 U1（证书 CN = `mqtt_server`，不是序列号，可据此排除）。

3. **Bambu Studio 走云还是走局域网**
   在 PowerShell 里看 BS 进程的已建立连接（`Get-NetTCPConnection -OwningProcess <bs pid> -State Established`）。
   实测只有 `47.100.40.179:8883` 与 `27.36.125.16:443` 两个外网地址 → **BS 连的是拓竹云端**。
   结合 `.108:8883` 能建 TCP 却永远不回 TLS ServerHello（「端口在监听、服务没起」的典型表现），
   判断打印机当前处于**云端模式**，没有对外提供局域网 MQTT。

**处置**：

- 打印机屏幕 → 设置 → 网络 → **局域网模式（LAN Only）**，开启后屏幕会显示访问码；
  此时本工具才能直连（Bambu Handy 的远程查看会失效，属预期）。
- 开启后如果 IP 又变了，不用手改：`printers._healBambuIp()` 会在连接失败时按**序列号**扫网段自动纠正。

**本次固化的代码**：

| 改动 | 位置 |
| --- | --- |
| 底层错误翻成带 IP 与处置建议的中文 | `printers._bambuErrorText()` |
| 网络类错误触发后台找 IP（按序列号精确匹配，5 分钟 / 6 轮节流） | `printers._isNetError()` / `_healBambuIp()` / `_findBambuBySerial()` |
| 证书 CN 读取超时 2.5s → 4s（嵌入式 TLS 握手偏慢） | `printers._bambuSerial()` |
| 错误文案与触发条件的单测（10 条） | `tests/printer-tests.js` [5] |

## 附 2：云端通道（2026-11-14）

打印机留在**云端模式**也能监控 —— 走拓竹云 MQTT，不再依赖局域网 8883。

| 项 | 说明 |
| --- | --- |
| 登录 | 设备页 → 「拓竹账号」→ 邮箱+密码（需要时补邮箱验证码）。密码只用于换 token，不落盘 |

| 云端端点 | `cn.mqtt.bambulab.com:8883`（TLS），订阅 `device/<serial>/report`，用户名 `u_<uid>`、密码 accessToken |
| 已知限制 | 接口非官方，字段变了要以实测为准；token 约 90 天过期，过期后设备卡提示重新登录 |
| 代码 | `src/core/bambucloud.js`（登录/设备列表）、`printers._pickChannel/_cloudConn`（双通道）、`components/bambuaccount.js`（登录弹窗）、IPC `bambuCloud*` |
| 建议 | 路由器里给打印机 MAC 绑定固定 IP，局域网通道就更稳；云端只是兜底 |

## 2026-11-19 · 四工具头温度 / 摄像头（快造 U1 + 拓竹）

### 一、四个头都要有温度

原先卡片只显示 `temps.nozzle`（当前活跃头）。U1 是四工具头机器，另外三个头有没有升温、有没有超温完全不可见。

实测报文（U1 @ 192.168.1.50，Klipper 2.0.0.205 / Moonraker 2.1.2）：

```
extruder  {temperature:245, target:245, extruder_index:0}
extruder1 {temperature:95,  target:95,  extruder_index:1}
extruder2 {temperature:42,  target:0,   extruder_index:2}
extruder3 {temperature:232, target:95,  extruder_index:3}
temperature_sensor cavity {temperature:45}
```

实现：

- `moonraker.extrudeNames()`：先 `/printer/objects/list` 看这台机器到底有哪几个 `extruder*`，再决定查哪些对象（对象名不存在时 `objects/query` 整条报错）。结果按 host 缓存 10 分钟。
- `status()` 把这些对象拼进查询；`temperature_sensor cavity` 存在时一并查（U1 有，普通 Klipper 机没有）。
- `_normalizeSnapmaker()` 输出 `temps.heads = [{index, cur, target, active}]`，`nozzle` 仍保留活跃头（兼容旧逻辑/监控采样），`chamber` 来自腔体传感器。
- 显示编号用**键位序**（extruder=0、extruder1=1…），不用对象里的 `extruder_index`：实测个别固件两者不一致，按字段取会出现两个头同时高亮（单测里就复现了）。
- 界面：四块 `T1..T4`，圆点用对应料盘颜色，当前头加淡底，有目标温度的加琥珀边框；热床与腔体排在下一行。

### 二、摄像头

**快造 U1** 没有拓竹那套 TCP 6000 隧道，实测它的画面来源是：

| 来源 | 实测 | 采用 |
| --- | --- | --- |
| `/server/webcams/list` | `webcams: []`（出厂未配） | 配过就用它的 `snapshot_url` |
| `camera/monitor.jpg` | 存在，JPEG 58–78 KB | 默认走这条 |
| `http://<ip>/webcam/?action=stream` | 502（nginx 上游没起来） | 不用 |

新增 `src/core/camera-http.js`：

- `httpFrame(url)` 同时支持 **JPEG 快照**与 **MJPEG**（长连接不结束，读到第一帧 `FFD9` 就主动断开）。
- `snapmakerFrame()` 优先级：用户填的 `cameraUrl` → Moonraker webcam → `camera/monitor.jpg`。
- **新鲜度按内容判断**：`monitor.jpg` 会出现「内容更新了但 `modified` 没变」，只看时间戳会把实时画面误判成 3 小时前的旧图。现在比较前后两帧字节，内容变了就重置计时；连续不变超过 2 分钟，卡片上出现「画面停在 X 分钟前」角标。

**拓竹** 继续走原有 TCP 6000 帧流（A1/P1 系列）；现在任何机型都显示「摄像头 / 打印机检测」按钮，取不到画面时把原因直接写在卡片里，并提示可在「编辑」里填摄像头地址。

**通用入口**：设备「编辑 / 添加」新增可选的「摄像头地址（快照或 MJPEG）」，任何不在支持列表里的机器都能接进来。

**打印机检测**：U1 也支持（抓两张、间隔 3 秒）；检测完成**自动弹出对比窗**，不再要求点第二次「查看图片」。若两张来自停更的静态快照，弹窗里会明确写出「画面停在 X 分钟前」。

### 三、关闭检测后画面必须消失（用户报的 bug）

现象：点检测弹窗「关闭」后，卡片里的实时画面还留着。

根因：`showDetect()` 只关弹窗，没有停摄像头轮询、也没清 `camFrames`；而且「关闭画面」按钮同样只停轮询、不清画面——文案与行为不一致。

修法：

- `stopCam(id)`：停轮询 + 删画面 + 删错误 + 重绘回「点摄像头查看」。
- 「关闭画面」与检测弹窗的**三条关闭路径**（按钮 / Esc / 遮罩）都走 `stopCam`。
- 关闭设备面板（`stopAllCams`）也清空所有画面缓存，下次打开是干净状态。

### 五、U1「亮灯打印却显示熄灯黑图」的真相（2026-11-19 二次排查）

用户反馈：正在打印、腔体灯亮，卡片里却是一张熄灯的黑色旧图。**原因不是我们画错，而是把一张停更 4 小时的静态文件当成了实时画面**：

- 真机 `monitor.jpg` 的 `modified` 是 18:42，抓图时 22:37，文件 58 KB 一字未变；
- 旧的新鲜度逻辑「首次抓到就把 `at` 记成 now」，所以 `staleSec=0`，界面连「画面停在…」角标都不显示；
- 复制到 `u1-klipper` / `u1-moonraker` 开源源码后确认：U1 摄像头走 MQTT JSON-RPC（`camera/request` / `camera/response`，方法 `camera.take_a_photo` / `camera.detect_capture`），**只有照片服务在跑、且有人请求时才会写 `monitor.jpg`**；默认状态下没有常驻 MJPEG 流。

实测过的端点（U1 192.168.1.50）：

| 端点 | 结果 |
| --- | --- |
| `http://<ip>/webcam/?action=stream`（80 端口） | 502（nginx 上游摄像头服务没启动） |
| `http://<ip>:8080/?action=snapshot` / `stream` | 连接拒绝 |
| `:7125/webcam/*` | 404 |
| `:7125/server/webcams/list` | `webcams: []`（出厂没配） |
| `:7125/server/files/camera/monitor.jpg` | 200，但可停更数小时 |
| `:1884` MQTT + `camera.take_a_photo` | CONNACK 正常，但 `camera/response` 无回包（摄像头服务未启动） |
| Moonraker G-code `TIMELAPSE_TAKE_FRAME` | 返回 ok，`monitor.jpg` 仍不更新 |

**转机：从打印机日志里找到了活路。** `unisrv.log` 显示摄像头服务其实一直活着：`camera/request` 上的 `camera.take_a_photo` 约 500ms 就回 `state:success`；`klippy.log` 里有一次成功的 `pic_20261119_145628.jpg`。对照 `u1-klipper` 的 `extras/timelapse.py`，G-code `TIMELAPSE_TAKE_FRAME DEBUG=1` 会让摄像头**当场拍一张**，写到 `/userdata/gcodes/pictures/pic_<YYYYMMDD_HHMMSS>.jpg`，可用 Moonraker 的 `/server/files/gcodes/pictures/...` 读到，读完还能 `DELETE` 清掉。实测拿到 89–101 KB 的亮灯打印实拍（见 `docs/screenshots/54-U1实时抓拍画面.png`），不再是黑图。这条路径不启动延时摄影、不改打印机设置、不会暂停打印。

**最终方案：主动抓拍 + 静态快照兜底。** 改动：

1. `camera-http.js` 重做新鲜度：首次抓取信文件 `modified`；内容变了信本次抓取（兼容 mtime 不更新的固件）；内容没变信 `modified`，不再把旧图记成「刚刚拍的」。
2. 返回 `static:true`，卡片显示「静态快照」角标 + 「画面停在 4 小时前」+ 一条中文说明（可在「编辑」里填自己的快照 / MJPEG 地址）。
3. `snapmakerFrame()` 在 `monitor.jpg` 之前多试四个常见 mjpg-streamer 地址，失败缓存 60 秒；Moonraker webcam 同时认 `snapshot_url` 与 `stream_url`。
4. 设备「编辑」里的示例地址不再用已实测 502 的 `/webcam/?action=stream`。

真机复测：`snapmakerLiveFrame()` 返回 `source=u1-live, staleSec=0`，单帧约 1.4 秒（含 1.1 秒等待），拿到的是亮灯打印中的工位实拍；连续调用 15 秒内命中缓存。主动抓拍失败时才退回 `monitor.jpg`，此时 `static=true, staleSec=14204`（约 3.9 小时），卡片显示「静态快照」「画面停在 4 小时前」及说明，见 `docs/screenshots/53-U1静态快照与陈旧提示.png`（兜底态）。

节流：15 秒最多拍一张，照片读完立即 `DELETE`，不会在打印机 eMMC 上攒文件。「打印机检测」用 `snapmakerLiveTwo()` 间隔 3 秒抓两张真·不同帧。
