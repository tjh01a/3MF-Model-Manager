# 快造 U1 转换（BedReady）· 调研结论与实施计划

> 目标：在 PrintShelf 里打开模型时，可以选择「用拓竹打开」，也可以选择「用快造打开」——后者先把拓竹 3MF 转换成快造 U1 能正确识别并正确切片的中文环境 3MF，再交给快造 Orca。
>
> 本文只记录**实测得到的事实**。凡是没跑出结果的，都标了「未验证」。

---

## 一、一句话结论

BedReady 的转换引擎**可以**直接搬进 PrintShelf 主进程离线运行（纯 JS，无网络、无浏览器依赖）。但**网页版的默认模式产出的文件，快造 Orca 2.4 是拒绝切片的**；只有把模式切到「套用 U1 样板」并补上启动器侧的预设合并，产出才真正可用。

另外：**只改耗材预设名不会改变任何打印参数**——3MF 里 `filament_settings_id` 只是「来源标签」，真正生效的是内嵌在 `project_settings.config` 里的数值。要让「拓竹petg」生效，必须把预设参数解析后合并进配置。

---

## 二、BedReady 是什么

| 项 | 事实 |
| --- | --- |
| 仓库 | `github.com/BedReady/bedready`，MIT |
| 形态 | Next.js 网页应用，转换跑在浏览器 Web Worker 里 |
| 核心文件 | `src/lib/convert.ts`（2904 行） |
| 公开入口 | `cleanThreeMF(file, target, opts)` → `{ blob, diff, … }` |
| 内部函数 | `retargetThreeMF(entries, machine, opts)` 只负责「同族换机」，**不是** U1 转换入口 |
| 依赖 | 仅 `fflate`（纯 JS zip），`three` 只在预览路径用到 |
| 机器定义 | `src/lib/targets.ts`，U1 样板来自 `u1-profile.json`（真机导出的 572 键配置） |
| 官方验收 | `scripts/slicer-golden.mjs` —— 用真实切片器的 CLI 切一遍，再断言 G-code |

它的本质不是「改几何」，而是**改切片器配置 + 重映射颜色槽位**，然后把 zip 重新打包。原文件不改动。

## 三、实测过程与四个关键发现

### 3.1 引擎可以离线跑在 Node 里

用仓库自带的 esbuild 把 `convert.ts` 及其依赖闭包（`targets` / `paint` / `prusa-project` / `color-bands` / `swap-pauses` / `filament-mixer` / `mixed-filament` / `u1-profile.json`）打成单个 CommonJS 文件：

```
产物 vendor/bedready/bedready-node.cjs   152 KB
```

唯一需要处理的是它在最后一步返回浏览器 `Blob`——Node 18+ 原生支持 `Blob`，直接 `await blob.arrayBuffer()` 即可，无需改动。

### 3.2 ⚠️ 关键发现一：网页版产物被快造 Orca 2.4 拒绝

拿你提供的两份文件做对照，用你本机的快造 Orca CLI 实测：

```
snapmaker-orca.exe --allow-newer-file --slice 1 --outputdir <dir> <file>
```

| 输入 | 结果 |
| --- | --- |
| 快造原生文件 `Glacier_Guardian_Snowy_Owl_U1.3mf` | ✅ 切成 167 MB G-code（说明 CLI 是可用的裁判） |
| 拓竹原始文件 | ⚠️ 能切，但按拓竹 P1S/X2D 的 256 床、拓竹温度切——机器是错的 |
| **网页版转换产物 `网页版处理转换成快造u.3mf`** | ❌ `process not compatible with printer.` |

也就是说：网页版提示「转换成功」，但 Orca 在切片那一刻并不认。

**根因**（逐键对比原生 U1 与网页版产物后定位）：

| 键 | 原生 U1 | 网页版产物 |
| --- | --- | --- |
| `print_compatible_printers` | `["Snapmaker U1 (0.4 nozzle)"]` | `["Bambu Lab X2D 0.4 nozzle"]` |
| `upward_compatible_machine` | `[]` | 7 台拓竹机型 |

Orca 的 `is_compatible_with_printer()` 就是读 `print_compatible_printers`。BedReady 网页版默认走 `preserve` 模式（保留原作者设置、只换机器身份），这两个键没被列入「打印机身份键」，于是拓竹的值被原样留下。

### 3.3 关键发现二：`stamp` 模式是对的

BedReady 的 `u1-profile.json` 里这两个键**本来就是正确的**：

```
print_compatible_printers = ["Snapmaker U1 (0.4 nozzle)"]
upward_compatible_machine = []
printable_area            = ["0.5x1","270.5x1","270.5x271","0.5x271"]
nozzle_diameter           = ["0.4","0.4","0.4","0.4"]
```

改用 `{ mode: 'stamp' }` 后，输出直接通过切片：

| 输入 | 源体积 | 输出 | 耗时 | 切片结果 |
| --- | --- | --- | --- | --- |
| `三角洲×影之刃-黑伤AMS-多色版 (1).3mf` | 50.3 MB | 52.2 MB | 12.7 s | ✅ 20.0 MB G-code |
| `蜘蛛侠2099.3mf` | 181.8 MB | 187.5 MB | 26.6 s | （retarget 模式，仅作性能参考） |

G-code 回显确认：`printer_model = Snapmaker U1`、`printable_area = 0.5x1,270.5x1,...`、4 工具头、`print_settings_id = 0.20 Standard @Snapmaker U1 (0.4 nozzle)`、`print_compatible_printers` 正确。

**结论：转换一律用 `stamp` 模式。**

### 3.4 ⚠️ 关键发现三：改预设名不等于改参数

同一份 stamp 产物，只把 `filament_settings_id` 从 `Generic PLA` 改成 `拓竹petg`，两次切片结果：

| | `filament_settings_id` | 喷嘴 | 热床 |
| --- | --- | --- | --- |
| A | `Generic PLA` | 220 °C | 65 °C |
| B | `拓竹petg` | 220 °C | **65 °C** |

**完全一致。** 说明 3MF 里的 `filament_settings_id` 只是溯源标签，Orca 加载项目时用的是配置里内嵌的数值，不会去预设库里重新解析。

你的 `拓竹petg.json` 只覆盖了 23 个键（流量比 0.94/0.955、最大体积速度 13/30、回抽、风扇），继承自 `Snapmaker PETG HF`。要让它真正生效，必须把继承链解析出来、把数值合并进 `project_settings.config`。

继承链已实测可解析：

```
拓竹petg  →  Snapmaker PETG HF (245°C / 70°C / MVS 20,30)  →  @U1 base  →  fdm_filament_petg_hf_category  →  fdm_filament_common
```

系统预设库位置：`<Orca 安装目录>/resources/profiles/Snapmaker/filament/`（316 个文件）
用户预设位置：`%APPDATA%\Snapmaker_Orca\user\default\{filament,process}\*.json`

### 3.5 关键发现四：800 MB 解压上限是浏览器护栏

`MAX_ZIP_COMPRESSED = 200 MB` / `MAX_ZIP_INFLATED = 800 MB` 是为了防止浏览器标签页被 zip 炸弹打爆。实测你库里的大文件：

| 文件 | 压缩后 | 解压后（文本类） |
| --- | --- | --- |
| `蜘蛛侠2099.3mf` | 181.8 MB | 852.4 MB |
| `warcraft_chess_set.3mf` | 191.1 MB | 1191.1 MB |
| `Human_Hero_Pack.3mf` | 189.8 MB | 1168.0 MB |

桌面端必须放宽，否则一半的模型直接转换失败。实测放宽到 3 GB 后，181 MB 文件峰值 RSS 仅 0.61 GB，完全可控。

## 四、方案设计

### 4.1 模块划分

```
vendor/bedready/
  bedready-node.cjs      # esbuild 产物（152 KB，含 fflate 与 U1 样板）
  LICENSE                # MIT 原文
  SOURCE.md              # 上游 commit、构建命令、打过的补丁

src/core/
  orcapresets.js         # 读取快造预设：列举用户预设、解析继承链、取值合并
  u1convert.js           # 转换核心：stamp 转换 → 配置后处理 → 缓存

electron/
  services.js            # 接线 u1convert / orcapresets
  ipc/index.js           # 新增 u1* 与 modelOpenWith 通道
```

### 4.2 转换流水线

```
① 读源 3MF（本地磁盘，不上传）
② cleanThreeMF(file, 'u1', { mode: 'stamp' })
③ 配置后处理（补 BedReady 遗漏的启动器侧键）
     print_compatible_printers = [U1 的 printer_settings_id]
     upward_compatible_machine = []
     print_settings_id / default_print_profile = 用户进程预设（若已选）
     filament_settings_id = 用户耗材预设 × N
④ 预设参数合并：解析继承链，把喷嘴温度/热床/流量/风扇/回抽…按槽位展开写入
⑤ 写出到缓存目录（绝不覆盖原文件）
⑥ 交给快造 Orca 打开
```

### 4.3 缓存策略

- 目录：`<数据目录>/u1-cache/`
- 键：`源路径 + 修改时间 + 大小 + 预设签名` 的 SHA-1 前 16 位
- 命中直接打开，不再转换；源文件改动或换预设自动失效
- 缓存可随时清空，删了只会重新转一次

### 4.4 打开方式

- **用拓竹打开**：直接把原始 3MF 交给 Bambu Studio（现有行为，不变）
- **用快造打开**：先 `ensureConverted()`，再把产物交给快造 Orca
- 首次使用时弹选择器；可在设置里指定默认，卡片上的打开按钮按默认执行，右键菜单始终提供另一种

### 4.5 安全红线

1. 原文件**只读**，任何情况下不写回、不移动、不删除
2. 转换产物只写进 `u1-cache/`，文件名带内容哈希，不会撞名
3. 不联网：引擎打包在本地，`/api/*` 那几个端点在本构建里没有任何调用点
4. 失败时给出可读中文原因，不静默降级成「假装成功」

## 五、验收标准

| 编号 | 标准 | 判定方式 |
| --- | --- | --- |
| U1-A1 | 快造原生文件仍能正常切片 | CLI 切片成功（对照组，已通过） |
| U1-A2 | 拓竹源经转换后能被快造 Orca 接受 | CLI 切片退出 0，无 `process not compatible` |
| U1-A3 | 输出声明为 U1 | `printer_settings_id` / `print_compatible_printers` / `printable_area` 正确 |
| U1-A4 | 颜色与涂色不丢 | 颜色数一致、`paint_color` 保留 |
| U1-A5 | 用户预设真正生效 | G-code 回显的温度/流量与预设解析值一致 |
| U1-A6 | 原文件字节不变 | 转换前后 SHA-1 相同 |
| U1-A7 | 缓存命中不重复转换 | 二次打开耗时 < 100 ms |
| U1-A8 | 大文件不失败 | 181 MB 文件转换成功 |
| U1-A9 | 无网络 | 断网可转换 |
| U1-A10 | 「用快造 U1 打开」在真机上跑通 | UI 走查脚本点击右键菜单 → 转换 → 真启动快造 Orca，Toast 显示成功 |
| U1-A11 | 设置里一个切片软件都没配也不炸 | 探测到的项以临时对象直传 `open()`，用成功后自动写回设置 |
| U1-A12 | 手动填安装目录也能用 | 「浏览」粘 `C:\Program Files\Snapmaker_Orca` 自动纠正为 `…\snapmaker-orca.exe` |

### 5.0 ⚠️ 关键发现五：BOM 让系统预设静默消失（2026-11-14）

`<安装目录>esources\profiles\Snapmaker\process .20mm Standard @Snapmaker U1 (0.4 nozzle).json`
和 `fdm_process_common.json` 的**首个字节是 UTF-8 BOM**（`EF BB BF`）。原实现：

```js
try { o = JSON.parse(fs.readFileSync(full, 'utf8')); } catch (_) { continue; }
```

`JSON.parse` 抛 `Unexpected token '﻿'`，被 `continue` 吞掉 —— 该预设从索引里彻底消失。
后果不是「少一个系统预设」，而是**链式坍塌**：U1 的全部工艺预设都 `inherits` 这两个文件，
所有继承它的用户预设都变成孤儿（UI 列表里看不到、`resolve()` 拿不到父级参数）。

判定方法：`node tools/preset-report.js` 会逐个走 `inherits` 链，打印 `missing`。
修法：`readJsonFile()` 去 BOM 再解析（`orcapresets.js`）。

### 5.1 上线后修掉的两个问题（2026-11-13）

**① 点「用快造 U1 打开」报出安装路径。** 用户看到的是 `C:\Program Files\Snapmaker_Orca` 这串字。三条线索：

1. `detect()` 每次返回的 id 都是新造的随机值（`sl_mwf83jgc_0c1cdc`），拿它回设置里查必然查不到 —— 设置里一个切片软件都没配时，几乎每条打开路径都会掉进这个坑。
2. `validate()` 对**目录**给出的理由是「不是有效文件：<原路径>」，而人在设置页手动填路径时，从资源管理器地址栏复制出来的正好是目录。
3. `_pick()` 只会按 id 查，没有任何「直接用一个对象」的入口。

修法：`open` / `openPaths` 增加 `{ slicer }` 形参；`_slicerByHint` 缓存探测结果并标 `__transient`；成功启动后 `_persistSlicer()` 把它写进设置并 Toast 告知；`validate()` 遇到目录时用 `_resolveExeIn()` 找里面的切片软件本体，找不到才报「这是文件夹，里面没找到 .exe」。

**② 转换产物被自己的扫描器当模型入库。** 数据目录 `…\PrintShelf\data` 正好落在监控文件夹 `D:\AI工具workbuddy` 内部，于是每次转换生成 `data/u1-cache/xxx_U1_<hash>.3mf` 都会被扫进库，库里多出一条「xxx_U1_…」的重复条目。修法：`Scanner._selfDirs()` 把 `thumbs / backups / logs / u1-cache` 无条件加进排除表；已误入库的历史记录用 `tools/clean-cache-records.js` 清出索引（磁盘文件保留）。

回归测试：`tests/run-tests.js` 加「粘目录自动找 exe」「不扫自身产物目录」两组（44 → 48）；`tests/u1-tests.js` 加「打开路径」整节，含临时对象、假 id、`.cmd` 分支、零配置四种情形（43 → 54）。UI 走查脚本 `tools/probe-u1-open.js`、`tools/probe-settings.js` 可重复执行。

## 六、明确不做

- 不做反向转换（快造 → 拓竹）
- 不做多打印机切换（BedReady 注册表里有其它机型，但只有 U1 是经过打印验证的）
- 不自动上传任何文件（网页版有个「服务端兜底」按钮，我们不接）
- 不改几何、不做减面/平滑（那是「模型优化」功能的事，两者互不干扰）
- 不擅自改用户预设本身
