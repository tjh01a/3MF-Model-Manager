# 12 · 预设词库自动分类 · 调研与计划书

> 日期：2026-11-15
> 需求来源：用户「在分类区加入一套预设词库，导入新 3MF 自动命中词库分类；用户可自己改词库（入口在设置）；每次打开软件对未分类的自动分类一次」。

---

## 1. 需求拆解

| # | 需求 | 落地方式 |
| --- | --- | --- |
| R1 | 一套预设词库 | `src/core/classify.js` 内置 `DEFAULT_RULES`，按分类绑定关键词，首次启动自动落到设置里 |
| R2 | 导入新 3MF 自动分类 | 扫描 worker 构造记录后、写库前即时匹配（纯内存，零额外 IO） |
| R3 | 用户可改词库 | 设置页新增「自动分类」tab：每个分类一个关键词框，可增删改，可一键恢复预设 |
| R4 | 每次启动对未分类自动分类一次 | `services.init()` 后调度一次批量分类（异步、不阻塞首屏） |

## 2. 调研结论（代码现状）

| 关注点 | 现状 | 结论 |
| --- | --- | --- |
| 记录构造 | `src/core/scanner.js` worker 内组装 `record`，含 `title / fileName / relativePath / author / note / meta` | **R2 接入点**：在 `record.categoryId === undefined → null` 之后、`return` 之前就地匹配 |
| 写库 | 扫描结束一次性 `store.updateLibrary(mutator)`，mutator 内同步执行 | 分类在 worker 里算好，写库时不需要再 await；一次写盘、一次刷新 |
| 3MF 解析 | `src/core/model3mf.js` 的 `extractMeta()` 已解压读取 `3D/3dmodel.model` 与 `Metadata/model_settings.config` | 顺手提取对象名/零件名存 `meta.objNames`，让哈希名文件（`at=…`、`v2`、`final`）也能被词库命中 |
| 设置读写 | `store.updateSettings(patch)` 浅合并对象子键；`DEFAULT_SETTINGS.ui` 是事实白名单，无字段校验 | 新增独立顶层组 `classify`，不挤进 `ui` |
| 启动时机 | `electron/main.js`：`services.init()` → `registerIpc()` → `signalRendererReady()` | 在 `signalRendererReady()` 之后调度（同 `scheduleColorBackfill()` 模式），不拖慢首屏 |
| 侧栏 | `renderCategories()` 已按 `state.categories` 渲染，读 `stats.byCategory` 计数 | 分类结果写库后自动反映，无需改侧栏 |
| 分类色 | 分类有 `color/icon/order` | 预设规则只写 `categoryId`，不碰分类本身 |

**关键约束**（沿用项目红线）
- 主进程/核心层 CJS，渲染层 ESM，不能互引 `constants.js`；核心层用 `C = require('./constants')`。
- 所有库写入只走 `store.updateLibrary()`，不直接落盘。
- 预览/自动化不得改用户偏好：自动分类只改 `categoryId`（且只对空值），不碰其它字段。
- 渲染层拿不到 `state` 之外的数据，设置页编辑词库走 `settingsUpdate`。

## 3. 数据模型

```js
// settings.classify
{
  enabled: true,          // 总开关：关掉后扫描与启动都不自动分类
  onScan: true,           // 新导入/扫描时自动分类
  onStartup: true,        // 每次启动补一次未分类
  rules: [
    {
      id: 'rule_test',
      categoryId: 'cat_xxx',      // 绑定分类；分类被删则该规则跳过
      keywords: ['测试', '校准', '首层'],  // 命中任意一个即归入该分类
    },
  ],
  lastRunAt: 0,           // 上次批量分类时间（设置页展示）
  lastRunStat: { scanned: 0, assigned: 0, skipped: 0 }, // 上次结果
}
```

- **规则顺序即优先级**：数组靠前的先匹配，第一条命中即止。
- 预设词库只用于「首次生成」；之后以用户编辑后的为准，不再覆盖。
- 记录侧新增可选字段 `autoClassified: true`，用于区分「自动分的」与「人工分的」，支持一键撤销。

## 4. 匹配算法

```
haystack = [
  title, fileName, relativePath 的各级目录名,
  author, note, sourceUrl,
  meta.objNames 里的对象名/零件名
].join(' ').toLowerCase()

for (rule of rules) {            // 顺序即优先级
  if (!rule.categoryId) continue;
  for (kw of rule.keywords) {
    const k = kw.trim().toLowerCase();
    if (k.length < 2) continue;  // 单字关键词误伤太大，直接忽略
    if (haystack.includes(k)) return rule.categoryId;
  }
}
return null;                     // 不命中就保持未分类，不做兜底
```

**刻意不做兜底**：不命中就留「未分类」。全兜到「摆件装饰」会让用户失去「还有哪些没分」的信号。

## 5. 预设词库（按用户 134 个文件的真实内容设计）

规则顺序：测试校准 → 备件维修 → 功能件 → 唱片/绘画 → 摆件装饰。

| 分类（按名称锚定） | 关键词（节选，实际见 `classify.js`） |
| --- | --- |
| 测试校准 | 测试、校准、试打、首层、收缩率、拼接测试、测试条、benchy、flow、tolerance、temp tower、圆底测试 |
| 备件维修 | 备件、维修、替换、喷嘴、热床、皮带、风扇、主板、喷头、导轨、拖链、刮条、顶置安装、AMS |
| 功能件 | 支架、收纳、底座、托盘、挂钩、卡扣、理线、外壳、盒子、架子、固定、废料、安装、改装、配件、铲刀、刀架、笔筒 |
| 唱片/绘画 | 唱片、record、vinyl、disc、黑胶、melody、音频、音乐、lumina、ocarina、陶笛 |
| 摆件装饰 | 手办、模型、雕像、摆件、装饰、面具、头盔、刀、剑、箭、钥匙扣、挂件、生肖、版画、立牌、皇冠、高达、机器人、鹦鹉、猫头鹰、鱼、蛙、伊布、初音、蜘蛛侠 |

**命名锚定策略**：预设规则的 `categoryName`（如「唱片/绘画」）在首次生成时按当前分类名匹配成 `categoryId`；匹配不到的分类规则先跳过（用户新建同名分类后可用「恢复预设」补上）。用户改名分类不影响已生成的规则（id 稳定）。

## 6. UI 设计（设置 → 自动分类）

```
[开关] 新模型导入时自动分类          开
[开关] 每次启动补一次未分类          开
────────────────────────────────
规则（顺序即优先级，越靠前越先命中）
┌ 测试校准     [关键词框：每行一个，或逗号分隔]
│ 备件维修     [...]
│ 功能件       [...]
│ 唱片/绘画    [...]
│ 摆件装饰     [...]
└
[立即分类未分类]  [恢复预设词库]  [撤销全部自动分类]
上次运行：3 分钟前，扫描 134，分好 7，跳过 0
```

- 关键词框用 `<textarea class="textarea" data-rule="<ruleId>">`，失焦或点保存时写库。
- 规则行显示当前分类名与颜色点，与侧栏一致。
- 规则绑定分类用隐藏 `<select>`（列出全部分类）还是固定？**固定为生成时的分类**，避免误绑；分类被删时该行标「分类已删除，规则暂停」。

## 7. 触发时机

| 时机 | 行为 | 性能 |
| --- | --- | --- |
| 扫描（新增/变更文件） | worker 内对 `categoryId` 为空的记录匹配一次 | 每条 1 次字符串拼接 + N 次 includes，微秒级 |
| 应用启动 | `signalRendererReady()` 后 1.2s 调度 `classifyUncategorized()`；只处理 `categoryId` 为空的记录 | 134 条 < 5ms，一次性写库 |
| 设置页「立即分类」 | 同上，但由用户显式触发，返回统计 | 同上 |

**并发保护**：批量分类与扫描写库都走 `store.updateLibrary` 的写队列，天然串行；分类只改空 `categoryId`，不覆盖扫描新写入的值。

## 8. 安全与回退

| 风险 | 处理 |
| --- | --- |
| 误分类覆盖人工结果 | 只处理 `!rec.categoryId`；人工改过的分类永不改动 |
| 用户想撤销自动结果 | `autoClassified === true` 的记录可一键清空分类（只清这些） |
| 词库改坏了 | 「恢复预设词库」重建默认规则；编辑只影响后续匹配，不回改历史分类 |
| 分类被删除 | 规则保留但暂停（`categoryId` 指向不存在的分类时跳过），设置页给出提示 |
| 性能/启动变慢 | 启动分类延迟 1.2s、异步、单次写库；不阻塞首屏与启动动画 |
| 关键词太短误伤 | 长度 <2 的词忽略；预设里不写单字 |
| 用户不想用 | 总开关 `enabled=false`，扫描与启动都不跑 |

## 9. 验收标准

1. `classify.js` 单元测试：
   - 预设规则能覆盖用户现有 134 个文件中的大多数（用真实标题做样本断言，至少 60% 命中且无跨类误判）；
   - 只对空 `categoryId` 生效，已有分类不动；
   - 关键词大小写不敏感、`<2` 字符忽略；
   - 规则顺序优先于词库顺序；分类被删时跳过。
2. 扫描新文件后，新记录自动带上分类（端到端冒烟加一条）。
3. 启动补分类：构造 3 条未分类记录，跑 `classifyUncategorized`，命中数正确、只写一次库。
4. 设置页：5 行规则可见可编辑，保存后重新打开仍是新值；「恢复预设」能回到默认。
5. `npm run selftest` 0 失败；`node tools/syntax-check.js` 0 错误；既有探针不受影响。

## 12. 实施结果与偏差

> 实施日期：2026-11-15。新增 `src/core/classify.js`、`tests/classify-tests.js`、本文件、`docs/screenshots/30-自动分类设置.png`；接线改动清单见 `docs/09-实现说明书.md` **A.11.1**。
> 直接跑到的结果：分类测试 **51 通过 / 0 失败**，语法哨兵 **80 文件 / 0 错误**。其余回归项由维护者另行确认。

a) **规则顺序**：最终定为 **测试校准 → 备件维修 → 功能件 → 唱片/绘画 → 摆件装饰**，与 §5 一致，未做调整。

b) **新增「干跑」优化**：批量分类前先只读统计 `pending`，再试算 `wouldAssign`；两者任一为 0 都直接返回，不调 `updateLibrary`。计划书没写这一层，测试暴露了「库里只要留着一个永远匹配不上的未分类文件，每次启动都会白写一次 `library.json`」的问题。现在只有真能分到东西才写库。

c) **`meta.objNames` 已实现**：扫描时从 `3D/3dmodel.model` 的 `<object name>` 与 `Metadata/model_settings.config` 的 `name` 键提取，去重后最多保留 12 个、每个 ≤60 字。**旧记录不回填**——升级前入库的模型想用内部对象名匹配，需要重新扫描一次该目录。

d) **预设关键词实测数量**：测试校准 **15**、备件维修 **15**、功能件 **21**、唱片/绘画 **13**、摆件装饰 **39**。计划书 §5 只给了节选；单字（刀 / 剑 / 箭 / 鱼）按 §8 的「不足 2 字忽略」本来就不会生效，实际词库改用 `刀柄 / 刀刃 / 刀身`、`黑伤 / 虫箭`、`肥鱼` 等双字以上词。

e) **真实库实测**：**134** 条记录、**7** 条未分类；启动自动分好 **4** 条，剩下 **3** 条没有任何可判断的标题 / 目录 / 对象名，保持未分类。这 3 条正是「不兜底」要保留的信号，不应为了清零而硬塞。

f) **`lastRunAt / lastRunStat` 的写入时机**：只在 `assigned > 0` 时写 `settings.classify`，避免每次启动都写一次 `settings.json`。设置页的「上次运行」统计因此只反映真正分到东西的那一次。

g) **撤销边界**：`classifyUndo()` 只清 `autoClassified === true` 的记录，人工分类不动；没有可撤销记录时连库都不写。批量分类写库前会取当前分类 id 集合，命中已删除 id 的记录被置回 `categoryId: null`、`autoClassified: false`，不写无效 id。

h) **设置页首次打开「自动分类」页落盘**：`rules` 为空时，首次打开该 tab 会用内置预设按当前分类名解析，并经 `settingsUpdate({ classify: { rules } })` 落盘；之后以用户编辑为准，不再自动覆盖。「恢复预设词库」是显式重建，只改词库、不回改历史分类。

### §12.1 未匹配提示（需求追加后补做）

启动分类跑完后，如果还有模型一个词都没命中，弹**表单式列表**：每行是 3MF 缩略图 + 模型名 + 分类下拉（首项「跳过（保持未分类）」），底部「全部跳过 / 应用」。「应用」按分类分组走 `api.bulk(ids, { categoryId })`，同组只写一次库。改词条的入口不放在弹窗里，只留一句提示指向「设置 → 自动分类」。

- 开关 `classify.promptUnmatched` 默认开（设置页「有模型没匹配上时，打开软件提醒我」）。
- **放弃主进程推送方案**：`webContents.send('classify:unmatched')` 实测会撞上渲染层事件注册时序——诊断显示 `bound:true` 但 `hits:0`，事件丢失。改为渲染层首屏后 `api.classifyRun()` 主动查（只读 + 干跑，不写库）。
- **capture / 走查模式不自动弹**（`index.html?capture=1`），否则会挡住其它探针要点的按钮；需要截图时探针调 `window.__printshelfPromptUnmatched([...])` 手动触发。
- 每次运行最多弹一次，点「先不管」后本次不再出现。
- 弹窗组件：`components/modal.js` 新增 `choiceDialog()`（多按钮，Esc / 遮罩 resolve null）。
